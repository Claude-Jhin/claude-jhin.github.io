本文主题：把“播放请求”正式接到“每帧混音与设备输出”执行链

写在前面

前几篇我们一直在讲“谁进入播放池、谁被并发裁掉、谁拿到数据”。
这篇开始进入真正会影响最终听感的地方：Mixer 每一帧到底怎么工作。

如果把前面的流程比作“排队入场”，这里就是“真正演出”。
这一步看不清，很多延迟、爆音、参数不同步问题都很难解释。

本文问题

Audio Mixer 在一帧里到底做了什么，才会把上游的一堆 WaveInstance 变成设备可播放的缓冲？
更关键的是：参数更新为什么会“感觉慢半拍”。

先给结论：渲染侧是节拍器，不是许愿池

这篇先给一个很关键的心智模型：

AudioRenderThread 是按固定 block 节奏运行的“节拍器”。

它不会因为你刚改了参数就立刻打断当前 block。
所以“慢半拍”的本质往往不是错误，而是命令生效边界和 block 边界重合关系。

本文讨论范围

聚焦渲染主链：

  • 命令如何进入渲染队列
  • 队列如何在渲染周期被泵出
  • Source 如何进入 Submix 图
  • Submix 如何走向终端输出

不展开：

  • 具体效果器算法细节（第 7 篇只讨论路由与执行位置）

调用链图

渲染主线拆解：一帧里真正发生了什么

1) 队列阶段：先收命令

AudioRenderThreadCommand 把控制命令发送到渲染侧队列。
这一层是时序敏感点：命令何时入队，决定何时有机会生效。

2) 泵队列阶段：再执行命令

PumpCommandQueue 在渲染周期内处理队列。
如果命令入队时机卡在 block 边界后，听感上就可能延后一个处理块。

3) 混合阶段：源进 Submix 图

源经过 SourceManager 更新后进入 FMixerSubmix::ProcessAudio。
这一步会汇总源信号、应用路由、串联效果链。

4) 输出阶段：终端写入设备

根 Submix 最终通过 ProcessAudioAndSendToEndpoint 输出到设备后端。
这一步是“持续供数”，不是“再做一次语义决策”。

关键类型

  • FMixerDevice：Mixer 总控，持有 SourceManager、Submix 图、平台后端接口。
  • FMixerDevice::AudioRenderThreadCommand：把 GT/AT 的控制变更投递到音频渲染线程。
  • FMixerDevice::PumpCommandQueue：渲染周期里泵队列，确保变更在正确块边界生效。
  • FMixerSubmix::ProcessAudio：Submix 真正执行混合、路由、效果处理的入口。
  • FMixerSubmix::ProcessAudioAndSendToEndpoint：到达根节点后，送往硬件端点。

我会优先跟这条链：

FAudioDevice::StartSources -> FMixerDevice::AudioRenderThreadCommand -> FMixerDevice::PumpCommandQueue -> FMixerSubmix::ProcessAudio -> FMixerSubmix::ProcessAudioAndSendToEndpoint

我会怎么定位“参数晚生效”

  1. 记录参数提交时刻（GT）。
  2. 记录命令入渲染队列时刻。
  3. 记录 PumpCommandQueue 处理该命令的时刻。
  4. 对齐当时 block 序号，确认延迟是否恰好是 1~N 个 block。

如果延迟和 block 对齐高度一致，通常不是 bug，而是时序模型本身的结果。

常见误区

  1. 误区：音频参数应该像变量赋值一样立即生效。
    实际：渲染侧是块处理模型，存在天然生效边界。

  2. 误区：一切延迟都应该在 Mixer 里修。
    实际：上游命令提交时机同样关键，常常需要 GT/AT 协同优化。

  3. 误区：只看平均 CPU 就够了。
    实际：音频更怕瞬时峰值，偶发峰值也会造成可闻抖动。

本篇结论

Audio Mixer 是标准的 pull 模型：渲染侧按固定 block 取数并混音。
所以“什么时候把命令送进渲染队列”几乎和“命令值是什么”同样重要。

很多听感上的“突然跳一下”并不是算法问题，而是命令生效时机跨了一个 block。
理解这一点后，再看参数平滑和时序控制会顺很多。
