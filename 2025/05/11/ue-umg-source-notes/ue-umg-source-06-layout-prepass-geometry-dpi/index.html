本文主题：UMG 布局为什么“看起来随机”
核心问题：为什么会出现尺寸抖动、坐标错位、DPI 下偏移失真？

写在前面

布局问题最烦的地方在于：它经常不是“错”，而是“偶发错”。
同一套 UI，在 2K 屏和 4K 屏、窗口模式和全屏模式下，表现像两套系统。

这篇我会沿着 Prepass -> DesiredSize -> Geometry -> DPI 这条线，
把那些“看起来随机”的错位和抖动拉回到确定性语义里。

我常用的断点走法

  1. 在 ForceLayoutPrepass 下断，确认是否手工触发了额外 Prepass。
  2. 在 SlatePrepass 下断，观察 DesiredSize 何时更新。
  3. 对比 GetViewportScale 返回值，确认 DPI 缩放倍率。
  4. 对比布局坐标与渲染坐标，定位偏移发生阶段。

先看这一段源码

这两段对应两个关键事实：

  1. 布局是阶段性计算，不是“设置属性后立即全局稳定”。
  2. 你看到的屏幕坐标常常已叠加 DPI 缩放，直接比较局部坐标会出错。

最小复现实验（含反证）

实验 A：同帧新增子控件的显示延迟

  1. 在一次点击回调里动态 AddChild 10 个子控件。
  2. 不调用 ForceLayoutPrepass 观察当帧表现。
  3. 再调用 ForceLayoutPrepass 观察差异。

预期：
不做额外 Prepass 时，部分布局结果会在下一帧稳定；手工 Prepass 可提前稳定。

反证：
若“布局实时同步”成立，两种情况下同帧显示应无差异。

我在项目里反复见到的 3 个坑

坑 1：设置 Slot 后立刻读取 Geometry 一定准确

  • 根因：布局缓存尚未更新。
  • 修正：在布局阶段完成后读取，或在必要时手工 Prepass。

坑 2：坐标偏移一定是 Anchor 错

  • 根因：忽略 DPI scale 与局部/绝对坐标换算。
  • 修正：统一坐标空间，先确认是否被 viewport scale 二次放缩。

坑 3：Prepass 越多越稳

  • 根因：额外 Prepass 有 CPU 成本，滥用会放大布局开销。
  • 修正：只在“同帧新增并要求同帧可见”的关键路径触发。

现场排查顺序

  1. 检查是否在错误时机读取 Geometry。
  2. 检查是否存在多余 ForceLayoutPrepass。
  3. 检查 DPI 倍率是否符合预期。
  4. 检查局部坐标与绝对坐标是否混用。
  5. 检查动画与布局是否在同帧互相覆盖。

这一篇要带走什么

布局问题的根因大多不是“参数错一点”，而是“阶段认知错一层”。
掌握 Prepass -> DesiredSize -> Geometry -> DPI 这条链，
就能把大部分“UI 抖动玄学”还原为确定性问题。
