本文主题：UMG 渲染性能瓶颈到底卡在“画什么”还是“怎么组织画”
核心问题：Retainer/Invalidation 为什么有时提速、有时反而更慢？

写在前面

Retainer 和 Invalidation 是两个很常被“神化”的优化手段。
我自己就干过一次：加完以后以为会稳提速，结果 UI 峰值更高了。

后来回头看源码才明白，问题不在工具本身，
而在我们没有先分清动态层和静态层。

我常用的断点走法

  1. 在 TickAndDrawWidgets 下断，确认 UI 绘制进入点。
  2. 在目标热点控件的 OnPaint 下断，确认是否重复绘制。
  3. 在 Retainer 路径下断，观察是否按 phase 更新。
  4. 在 PaintInvalidationRoot 下断，确认是否走到 fast path。

理解这一段的关键点：
OnPaint 并不直接“画到屏幕”，它先写入 ElementList；批次与提交发生在后续阶段。
所以“看起来只画了一次”不等于“后端只提交了一次”。

最小复现实验（含反证）

实验 A：Retainer 分帧渲染收益测试

  1. 准备一个复杂静态面板（大量图标与文本）+ 一个高频动画角标。
  2. A 方案：全量实时绘制。B 方案：静态层放 Retainer，设置 Phase/PhaseCount。
  3. 对比 stat slate 与 GPU 提交开销。

预期：
静态区域占比高时，Retainer 可明显降低 UI 提交成本；动态区域占比高时收益下降。

反证：
若“Retainer 一定提速”成立，则动态占比提升后不应出现收益回落。

我在项目里反复见到的 3 个坑

坑 1：Retainer 是通用加速开关

  • 根因：忽略内容动态比例、RenderTarget 成本与更新频率。
  • 修正：先分离静态/动态层，再决定是否 Retainer。

坑 2：Invalidation 开了就不用管控件更新方式

  • 根因：频繁属性变化会持续打脏，导致缓存命中率低。
  • 修正：减少无意义状态写入，稳定树结构，提升缓存命中。

坑 3：只看单控件 OnPaint 次数就能判断性能

  • 根因：真正成本还包括批次拆分、材质切换、RT 更新。
  • 修正：把 OnPaint、Batch、RT 三层指标一起看。

现场排查顺序

  1. 识别 UI 热点是 CPU 组织瓶颈还是 GPU 提交瓶颈。
  2. 统计 Retainer 命中与重绘频率。
  3. 检查 Invalidation 是否频繁被无效状态写入打脏。
  4. 检查批次是否因材质/裁剪状态被过度拆分。
  5. 检查是否把高频动态内容错误塞进 Retainer。

这一篇要带走什么

UMG 渲染优化不是“多加组件”，而是“先分层再缓存”。
先判断内容变化模型，再选 Retainer/Invalidation，才不会出现“优化后更慢”。
