这篇为什么最重要

前 7 篇解决“怎么工作”。
第 8 篇解决“为什么线上会坏，以及如何不再反复坏”。

你真正要守住的是四类问题：

  1. 激活失败
  2. 依赖缺失
  3. 打包后资源缺失
  4. 多人不一致

四类故障的排障路径

1. 激活失败

  1. 看 LogGameFeatures 错误日志，确认停在哪个状态。
  2. 用 ListGameFeaturePlugins 检查当前状态与目标状态区间是否一致。
  3. 确认该 Feature 的依赖是否已到可激活状态。

2. 依赖缺失

  1. 先验证插件描述可读，排除 descriptor 读取/解析错误。
  2. 检查依赖名与 URL 解析是否一致。
  3. 关注策略过滤是否把依赖错误排除。

3. 打包后资源缺失

  1. 检查 GetPluginsToCook 结果是否包含目标 Feature。
  2. 检查 FilterInactivePluginAssets 是否误过滤资产。
  3. 确认 InstallBundle 名称（主包/可选包）与分发配置一致。

4. 多人不一致

  1. 核对 Client/Server 加载模式是否对齐（见第 7 篇）。
  2. 检查 Action 是否按 World Context 正确过滤。
  3. 区分“Feature 激活状态一致”与“业务复制状态一致”两层问题。

Lyra 最小复现（实验 8）

目标：形成一份可重复的上线前回归脚本。

  1. 选择一个 Lyra 风格玩法 Feature（含组件、输入、UI、能力）。
  2. 在三种环境跑一遍：Editor PIE、Standalone、Dedicated Server + 2 Clients。
  3. 每种环境执行一次激活、停用、再激活。
  4. 固定产出三类证据：状态快照、关键日志、表现录屏。
  5. 把结果写入回归表，每次版本更新跑同一脚本。

上线前检查清单（建议）

  1. ListGameFeaturePlugins 快照保存。
  2. 关键 Feature 的状态切换日志可追溯。
  3. Cook 产物里已确认目标 Feature 资源存在。
  4. Client/Server 双端加载模式已验证。
  5. 停用路径和二次激活路径均通过。

原理下钻：Cook 链路里的“收集”和“过滤”是两步

很多线上问题都来自把这两步混为一谈：

  1. 收集：哪些 GameFeature 插件/资产应进入构建候选集。
  2. 过滤：在当前状态与策略下，哪些资产应从候选集中剔除。

只有先收集再过滤，你才能解释“编辑器能跑、打包丢资源”的根因。

热更治理建议（InstallBundle 视角）

  1. 主包和可选包命名要稳定（GetInstallBundleName / GetOptionalInstallBundleName）。
  2. 版本升级时优先保证依赖 Feature 的包一致性，再做单包增量。
  3. 失败重试策略要与状态机取消语义一致，避免“包层重试成功但状态机已终止”。

排障执行顺序（建议固化成 Runbook）

  1. 描述文件合法性（能否读、能否解析）
  2. 插件候选集（是否被识别为有效 GameFeature）
  3. 构建候选集（是否进入 Cook）
  4. 运行时状态（是否到达目标状态区间）
  5. 业务表现（是否完成多人一致）

把顺序固定下来，团队就不会在第 5 步发现问题时直接跳回改业务代码。

回归基线建议（量化）

  1. 状态指标：激活成功率、停用成功率、平均激活耗时。
  2. 资源指标：Feature 相关资产缺失率、包体增量波动。
  3. 多人指标：晚加入一致性通过率、跨地图一致性通过率。
  4. 稳定性指标：连续 20 次激活/停用循环无泄漏。

旗舰文尾声：把排障从“个人经验”变成“团队资产”

这一篇真正想解决的不是“这次怎么修”，而是“下次别再同样地坏”。
建议你把下面四份资产固化到仓库而不是口头传承：

  1. GameFeature 调试 Runbook
  2. Cook/Chunk 校验脚本
  3. 多人一致性回归脚本
  4. 上线前检查清单模板

只要这四份资产在，团队迭代速度和稳定性都会明显提升。

可直接落地的回归节奏

如果你们每两周发一次版本，可以这样排：

  1. T-10 天：跑 Feature 状态机回归（激活/停用/重入/依赖）。
  2. T-7 天：跑资源回归（Cook、Chunk、包体差异、缺失资产）。
  3. T-5 天：跑多人一致性回归（晚加入、切图、重连）。
  4. T-2 天：跑压力回归（高频启停、长会话、并发玩法切换）。
  5. T-1 天：冻结策略配置，导出最终状态快照。

把节奏固定下来之后，你会发现“线上突发回滚”频率会明显下降。

一套能复用的故障复盘模板

每次故障复盘都坚持填下面 6 项：

  1. 触发条件（操作序列 + 环境）
  2. Feature 状态轨迹
  3. 业务状态轨迹
  4. 资源状态轨迹（包、资产、依赖）
  5. 修复方案与验证范围
  6. 防再发措施（脚本、规则、监控、测试）

复盘模板的价值在于“可累计”，三个月后你会得到非常真实的风险地图。
