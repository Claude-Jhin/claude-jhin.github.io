先定一个工程目标

我们希望某个玩法包激活后：

  1. 输入映射生效
  2. 对应 UI 面板出现
  3. 能力集被授予

停用后则完整反向收敛。
这就是 Lyra 风格 GameFeature 扩展的核心体验。

这篇最重要的设计建议

不要把输入/UI/能力三件事写在同一个 Action 里。
建议拆成三个独立 Action（或至少三个清晰的子模块），因为它们的失败与回滚语义不同：

  1. 输入映射失败通常可降级继续运行。
  2. UI 挂载失败可能只影响表现，不该拖垮核心功能。
  3. 能力授予失败通常是硬失败，需要强提示和回滚。

Lyra 最小复现（实验 6）

目标：在 Lyra 工程复现“同一 Feature 管理三类扩展”。

  1. 自定义一个 UGameFeatureAction 派生类（或按 Lyra 现有扩展 Action 拆分）。
  2. 激活时执行：
    • 给本地玩家添加输入映射
    • 向 UI 容器添加功能页签
    • 给 ASC 授予一组能力
  3. 停用时执行反向操作，确保重复激活不累积脏状态。
  4. 在日志里区分三类扩展的成功/失败，避免“只看总成功”。

常见坑与检查项

  1. 只实现激活，不实现停用，测试环境看不出问题，长局游戏必炸。
  2. 输入/UI 放在服务器路径执行，结果 Dedicated Server 无意义报错。
  3. 能力授予不做去重，重复激活后同能力被多次授予。

原理下钻：三类扩展的“句柄化回收”

要把这篇真正写成长文，最关键是统一“句柄/引用追踪”思路：

  1. 输入映射：记录 MappingContext + Priority，停用时精确移除。
  2. UI 挂载：记录创建的 Widget 实例或容器句柄，停用时销毁或出栈。
  3. 能力授予：记录 FGameplayAbilitySpecHandle，停用时按句柄撤销。

这三个系统都支持“增加”很容易，但“正确回收”才是难点。

推荐的 Action 设计模板

长文里建议给出一个统一模板，读者可以直接套：

  1. OnGameFeatureActivating(Context)
    收集目标对象 -> 执行输入/UI/能力注入 -> 保存回收句柄。
  2. OnGameFeatureDeactivating(Context)
    按逆序回收：先 UI，再输入，再能力（或按你的依赖顺序）。
  3. 失败策略
    每步记录成功/失败，确保部分失败时仍可进入可恢复状态。

调试手册（建议）

  1. 输入：观察 RequestRebuildControlMappings 是否被触发。
  2. UI：记录 Widget 创建与销毁数量，检查长局是否泄漏。
  3. 能力：核对 GiveAbility 与 ClearAbility 句柄集合是否一一对应。
  4. 多次激活/停用循环 10 次，看是否有累积副作用。

进阶练习

在 Lyra 工程里做一个“事件模式 Feature”：

  1. 激活时新增一套输入、一个活动面板、两项能力。
  2. 停用后所有输入/UI/能力完全回滚。
  3. 中途切换 Pawn、切换地图后再次激活，验证句柄追踪仍正确。

本篇结论

Lyra 风格扩展的关键不是“会加功能”，而是“会回收功能”。
下一篇我们把这个问题搬到多人：同样的 Feature，为什么在客户端和服务端会出现不一致。

把“体验层扩展”做稳的关键：拆成三条独立回路

输入、UI、能力三件事看起来都在“激活时新增”，但回收条件完全不同：

  1. 输入回路：依赖本地玩家上下文，切 Pawn 时最容易出错。
  2. UI 回路：依赖视图层容器，切界面层级时容易残留。
  3. 能力回路：依赖权威与复制语义，最怕重复授予或越权清理。

如果你把它们混在一个大 Action 里，线上问题几乎必然“互相污染”。

推荐的句柄结构

你可以在 Action 内维护一个按玩家分组的上下文表：

  1. InputHandles：记录已添加的 MappingContext 与优先级。
  2. WidgetHandles：记录创建的 UI 实例或容器槽位。
  3. AbilityHandles：记录能力授予返回的 SpecHandle。

停用时按组回收，比“全局清空”安全太多。

断点剧本：专治“停用后还残留”

  1. 输入：断 RemoveMappingContext，确认每个 Add 都有对应 Remove。
  2. UI：断容器移除逻辑，确认对象销毁和引用释放。
  3. 能力：断 ClearAbility，确认句柄来自当前 Feature 而不是其他系统。
  4. 最后做一轮二次激活，确认不存在重复项。

进阶练习：做一套“跨局会话回收测试”

  1. 激活 Feature，执行输入/UI/能力注入。
  2. 不停用，直接切图、重生、切 Pawn。
  3. 再停用 Feature，核对三类句柄是否仍可正确回收。
  4. 回到主菜单再进局，重复一次。

这组测试最能提前发现长会话下的隐性泄漏。

附录：能力回收的权威边界提醒

很多项目在这里翻车：
客户端本地把能力加上去了，停用时又在客户端直接清，结果和服务器状态打架。

建议明确规则：

  1. 能力授予与清理由权威端控制。
  2. 客户端只做表现与输入侧处理，不直接越权改能力集。
  3. 任何本地预测都必须有被权威覆盖的路径。

这三条不写进规范，迟早会出现“某些玩家技能栏永远不干净”的问题。

附录：建议保留的运行时日志字段

为了后续复盘，建议每次注入都打这些字段：

  1. FeatureName
  2. PlayerId
  3. ActionType(Input/UI/Ability)
  4. HandleId
  5. ActivateOrDeactivate
  6. WorldContext

日志字段统一后，排障时能迅速把三条回路串起来。
