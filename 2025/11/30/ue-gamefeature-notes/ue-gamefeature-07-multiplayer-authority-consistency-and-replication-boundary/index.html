先给结论

GameFeature 在多人里最常见的问题不是“没加载”，而是“加载边界不一致”。

典型现象：

  1. 服务器激活了，客户端没表现。
  2. 本地玩家看见 UI，其他客户端没有。
  3. Dedicated Server 报一堆本应只在客户端执行的逻辑。

根因往往是三类边界没对齐：加载模式边界、世界上下文边界、复制边界。

三层边界怎么落地

  1. 加载模式边界：
    在 Policy 层决定哪些数据在 Client/Server 载入，不要把环境判断分散在每个 Action。
  2. 世界上下文边界：
    使用 FGameFeatureStateChangeContext 限定作用域，避免多世界或错误 World 污染。
  3. 复制边界：
    Feature 激活只负责“是否生效”，业务状态一致性仍由你的 Replication/RPC 设计保证。

Lyra 最小复现（实验 7）

目标：复现并修复“本地有表现，远端无表现”。

  1. 在一个 Feature 里同时放输入/UI/组件注入逻辑。
  2. 双客户端 + Dedicated Server 运行，激活 Feature。
  3. 人为把加载模式配置错（例如服务端不加载必要数据），观察差异。
  4. 再通过 Policy + Context 边界修正，确认行为收敛。

这个实验会非常直观地暴露“激活成功不等于多人一致”。

常见坑与检查项

  1. 把“是否激活”当作“是否同步”，忽略复制链路设计。
  2. 客户端专属逻辑未隔离，导致 Server 路径报错或空操作。
  3. Feature 停用后未撤销本地表现，产生“幽灵 UI/输入映射”。

原理下钻：多人下的三张矩阵

建议在长文中明确画出三张矩阵，避免语义混淆：

  1. 加载矩阵：哪些 Feature 在 Client/Server 加载。
  2. 激活矩阵：哪些 Feature 由谁触发状态改变。
  3. 表现矩阵：哪些行为是本地表现，哪些需要网络一致性。

如果三张矩阵没有独立定义，线上排障会不断把“加载问题”误判为“复制问题”。

权威与一致性的实操规则

  1. 权威规则：状态改变请求由服务端判定，客户端只发意图。
  2. 表现规则：本地可预测表现要能被权威结果覆盖与回收。
  3. 数据规则：Feature 激活不替代业务复制协议，状态一致性仍由 Replication/RPC 负责。

调试手册（多人专项）

  1. 先记录三端日志（Server / ClientA / ClientB）中的 Feature 状态轨迹。
  2. 再记录业务状态轨迹（例如技能可用标记、组件启停标记）。
  3. 对比两条轨迹是否同步：
    “Feature 同步但业务不同步”通常是复制层问题；
    “Feature 不同步”才是 GameFeature 层问题。

进阶练习

  1. 在 Dedicated Server 模式下激活一个带 UI 与能力注入的 Feature。
  2. 验证服务端仅走服务端必要逻辑，客户端走表现与输入逻辑。
  3. 故意制造客户端晚加入，确认其 Feature 状态与业务状态都能收敛。

权威矩阵示例（建议放到长文中）

场景 Feature 状态改变发起方 业务状态最终权威 客户端本地可预测
技能系统扩展开关 Server Server 可（需回收）
活动 UI 展示 Client（受控） N/A（表现层） 可
角色组件注入 Server 或策略统一调度 Server 部分可

这张表能帮读者区分“状态控制权”和“表现自主权”。

典型事故复盘模板

建议每次多人问题都按同一模板记录：

  1. 当时三端 Feature 状态（Server/ClientA/ClientB）
  2. 当时业务关键状态（能力列表、组件列表、UI 列表）
  3. 触发操作序列（谁先激活、谁后加入、是否切图）
  4. 最终归因层级（加载策略 / 上下文过滤 / 复制协议）

把模板固化后，排障速度会显著提升。

本篇结论

多人里的 GameFeature，本质上是“加载策略 + 上下文过滤 + 复制语义”三件事的交集。

长文加餐：一张“症状到层级”的速查表

现象 最可能层级 第一检查点
服务器有能力，客户端没有 复制层 / 授予路径 能力句柄是否复制到位
本地 UI 有，其他人没有 表现层 / 本地逻辑误入网络语义 UI 是否被当作全局状态
Dedicated Server 报输入错误 加载模式或上下文过滤 是否错误执行客户端专属逻辑
激活成功但部分玩家无组件 Receiver/世界上下文与时序 是否覆盖晚加入与切图路径

这张表的作用是：
先锁层，再动代码，减少盲目试错。

多人调试的一条铁律

永远把“状态一致”拆成两句话去验证：

  1. Feature 状态一致了吗？
  2. 业务状态一致了吗？

很多复盘失败，就是因为这两句混在一起。
Feature 一致不代表业务就一致；业务不一致也不一定是 Feature 的锅。

服务器权威下的实践建议

  1. Feature 的目标状态改变由服务器控制，客户端只请求。
  2. 客户端可做本地预表现，但必须有可撤销路径。
  3. 所有可见状态最终以权威结果收敛。
  4. 晚加入玩家要验证“状态重建”而不是只看实时广播。

进阶练习：晚加入一致性压测

  1. 先让房间运行 5 分钟，期间多次启停 Feature。
  2. 第 6 分钟让新玩家加入。
  3. 记录新玩家收到的 Feature 状态、能力状态、组件状态、UI 状态。
  4. 对比已有玩家，检查是否存在“历史状态未补齐”问题。

这组测试非常适合作为上线前必跑项。

附录：多人联调当天的最小记录模板

建议联调时每个人都按同一模板报问题：

  1. 时间戳
  2. 服务器状态
  3. 客户端状态
  4. 触发操作
  5. 预期结果
  6. 实际结果

不要省略时间戳。
没有时间戳，后续对日志和回放几乎无法精确对齐。

这个模板看似基础，但在多人问题里是效率乘数。
