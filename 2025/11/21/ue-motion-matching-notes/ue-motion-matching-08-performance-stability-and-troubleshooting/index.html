系列定位：UE5 Motion Matching 源码深挖（5.4/5.5）
本文主题：工程落地阶段的性能与稳定性方法论

写在前面

到这一篇，目标从“看懂系统”切到“把系统跑稳”。
很多团队在这个阶段会遇到三类问题：CPU 成本、匹配抖动、场景边界异常。

先把顺序定下来

优化顺序建议固定为：

  1. 先稳输入（Trajectory/PoseHistory）。
  2. 再控搜索空间（Database/Chooser）。
  3. 最后调采样密度与权重。

先后顺序反了，通常会陷入“越调越乱”。

主线图（排障流程）

先立一个统一目标

落地阶段不要只追求“看起来顺”，而要同时满足三个目标：

  1. 帧耗时可控（尤其是角色多实例时）。
  2. 姿态切换稳定（不高频抖动）。
  3. 结果可解释（出了问题能快速定位链路位置）。

这三点里，第三点最容易被忽略，但它决定团队迭代速度。

成本模型：为什么会慢

可以把运行时成本粗略看成：

成本 ~ 搜索空间大小 × 特征维度 × 查询频率

对应到工程动作就是：

  • 通过 Chooser 控制搜索空间。
  • 通过 Schema 控制特征维度与复杂度。
  • 通过稳定输入减少不必要重搜与抖动切换。

固定优化顺序（非常重要）

第一步：稳输入

先处理 Trajectory/PoseHistory 输入抖动。
输入不稳时，后面所有优化都可能被噪声吞掉。

第二步：控搜索空间

用多数据库与上下文规则缩小候选空间。
全库乱搜会同时伤害性能与命中质量。

第三步：调 Schema 与采样

最后再调 Channel 权重、采样密度、索引粒度。
这一步收益大，但前两步没稳住时很难调出稳定结果。

“慢、抖、怪”三类问题的快排路径

慢（CPU 压力高）

先看：

  1. 当前 Database 是否过大或选库过宽。
  2. Schema 维度是否过重。
  3. 是否存在不必要高频重搜。

抖（切换频繁）

先看：

  1. Query 输入是否抖动。
  2. 选库边界是否来回横跳。
  3. 切换判定是否过于激进。

怪（动作语义不对）

先看：

  1. 库覆盖是否缺失关键语义。
  2. Schema 权重是否偏离目标。
  3. 当前命中库是否正确。

建议长期保留的回归基线

至少保留一套固定场景，用来比较每次参数调整的影响：

  • 直跑 -> 急停
  • 匀速 -> 急转
  • 坡地转向
  • 上下文切换（空手 <-> 持枪）

每次调参只改一个因素，并记录：

  • 平均查询耗时
  • 切换次数
  • 主观观感备注

这样后续回滚和复盘会非常清晰。

我在项目里会做的排障演练

  1. 准备一套固定测试场景：直跑、急停、急转、坡地转向。
  2. 每次只改一类参数（输入、选库、采样、权重），记录帧耗时与错选现象。
  3. 使用统一日志模板记录“修改项 -> 结果变化 -> 是否回滚”。
  4. 完成一次“按固定顺序排障”的演练，并统计定位耗时。

如果过程记录得足够干净，你会很明显地看到：
按固定顺序排查后，定位速度会快很多，结果也更容易复现。

风险提示与延伸方向

  • 本系列首期不展开多人网络同步细节。
  • 若进入多人项目，下一阶段应补：网络复制策略、服务器权威下的轨迹一致性、回放校验。

一张可直接复用的排障清单

  1. 当前命中库正确吗？
  2. Query 输入曲线稳定吗？
  3. 切换事件是否异常频繁？
  4. Schema 权重是否偏离当前目标？
  5. 数据库是否覆盖当前语义动作？
  6. 调整是否有前后对照记录？

只要这 6 条能稳定执行，团队在 Motion Matching 上的迭代效率会明显提升。

源码里的性能关键点（UE5.5）

如果你要做“性能可解释”的优化，建议盯住这几处：

  1. PoseSearchDatabase.cpp 的 UPoseSearchDatabase::Search(...)
    入口分发 BruteForce / VPTree / PCAKDTree，这是第一层性能分水岭。
  2. 同文件 SearchBruteForce / SearchVPTree / SearchPCAKDTree
    三条路径都要经过候选过滤（PopulateNonSelectableIdx / PopulateSelectableAssetIdx）和 EvaluatePoseKernel。
  3. PoseSearchLibrary.cpp 的 UPoseSearchLibrary::UpdateMotionMatchingState(...)
    控制搜索节流（SearchThrottleTime）、继续姿态搜索、是否复用缓存查询通道数据。

这三点基本覆盖了“慢在哪、为什么慢、怎么降”的主问题。

直接可用的调试开关（引擎内置）

在 C:\Epic\UE_5.5 对应源码里，可以看到这些非常实用的 CVar：

  1. a.AnimNode.MotionMatching.DebugDrawInfo / ...DebugDrawInfoVerbose
    看当前库、当前资产、BlendStack。
  2. a.AnimNode.MotionMatching.DebugDrawQuery / ...DebugDrawCurResult
    直观看 Query 与命中姿态特征。
  3. a.MotionMatch.CompareAgainstBruteForce
    用于对照优化搜索与暴力搜索的结果一致性。
  4. a.MotionMatch.ValidateKNNSearch
    用于校验 KNN 搜索顺序与代价一致性（调试时很有用，线上别常开）。

最小性能实验（可复现）

  1. 固定同一数据库与输入场景，先跑 BruteForce 作为基线。
  2. 切到 PCAKDTree，记录查询耗时与命中差异。
  3. 打开 a.MotionMatch.CompareAgainstBruteForce，确认优化搜索没有引入异常偏差。
  4. 再通过 Chooser 缩小候选空间，比较“算法优化”和“候选收缩”哪一项收益更大。

这套实验做完，你会得到一份真正可落地的优化优先级，而不是凭体感调参。
