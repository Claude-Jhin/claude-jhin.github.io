系列定位：UE5 Motion Matching 源码深挖（5.4/5.5）
本文主题：上下文驱动的数据库选择策略

写在前面

当项目进入真实规模，通常不会只有一个 Database：
行走、战斗、负重、受伤、武器状态都可能要求不同候选空间。
Chooser 的价值，就是把“选库逻辑”从节点细节里抽离出来。

先说结论

多库系统的关键不是“库越多越好”，而是上下文边界要稳定、可调试。
Chooser 负责“先决定搜索空间”，Motion Matching 再在该空间中找最优姿态。

主线图（上下文决策链）

先把问题定性：多库不是可选项，而是规模化必选项

当项目从“单一移动系统”扩展到“多武器、多状态、多环境”时，单库策略通常会失效：

  • 库太大，检索空间噪声变高。
  • 语义冲突，导致同一 Query 在不该出现的动作里命中。
  • 调参牵一发而动全身。

所以多库方案不是炫技，而是控制复杂度的必要手段。

Chooser 在这里的真实价值

Chooser 的价值不在“能写条件”，而在“让条件成为可治理资产”：

  1. 条件集中可视化，不散落在多个 AnimGraph 节点。
  2. 上下文策略可版本管理，便于回归。
  3. 业务决策与检索参数解耦，协作边界更清晰。

换句话说，它是“选库治理层”，不是“另一个动画节点”。

一个实用的分库策略

建议按“语义边界明确且切换稳定”的维度分库，例如：

  • 行为维度：Locomotion / Combat / Traversal
  • 姿态维度：站立 / 蹲伏 / 负重
  • 装备维度：空手 / 单手武器 / 双手武器

不建议过细按碎片状态拆库，否则切库抖动风险上升。

切库策略的三个红线

  1. 避免边界抖动：切库条件必须有滞回或缓冲区。
  2. 避免隐式回退：每个上下文都应有明确 fallback 库。
  3. 避免全局耦合：新增一条规则不应影响无关上下文。

这三条做到，系统可维护性会明显提升。

一次典型调用顺序

可以把运行时理解成：

  1. Chooser 先根据上下文吐出 Database 集合。
  2. Motion Matching 在该集合里做评分检索。
  3. 命中结果再走切换判定输出。

因此“命中异常”先看 Chooser 决策，再看匹配评分，是最高效顺序。

我建议你这样验证

  1. 设计两个上下文：无武器移动、持枪移动。
  2. 通过 Chooser 显式切换到两套 Database。
  3. 在同一输入轨迹下，验证选库变化与动作风格变化是否一致，并确认切换时无明显抖动峰值。
  4. 在上下文边界值附近来回触发，检查是否出现“高频切库”。

如果链路没问题，你会很容易观察到：
上下文切换时先变化的是搜索空间，然后才是最终动作风格，定位也会更直接。

协作建议：程序、TA、动画三方如何分工

  • 程序：保证上下文信号稳定、可观测。
  • TA：维护 Chooser 规则资产与回归用例。
  • 动画：保证分库语义清晰、边界动作覆盖充分。

三方边界清楚，后续扩展新玩法时才能“加法迭代”，而不是全局返工。

源码级决策路径（UE5.5）

Chooser 的核心逻辑在：

C:\Epic\UE_5.5\Engine\Plugins\Chooser\Source\Chooser\Private\Chooser.cpp
UChooserTable::EvaluateChooser(...)

它的实际顺序是：

  1. 先收集未禁用行。
  2. 逐列执行 Column.Filter(...)，得到候选行集合。
  3. 如果有代价列，执行排序。
  4. 对命中行执行结果，并触发 Column.SetOutputs(...)。
  5. 若无命中，走 FallbackResult 并设置 fallback 输出。

这说明 Chooser 不是“if-else 工具”，而是“过滤 + 评分 + 输出回填”的结构化决策器。

它如何接到动画节点

AnimNode_ChooserPlayer.cpp 里有两个关键点：

  1. FAnimNode_ChooserPlayer::ChooseAsset(...)
    常规路径是 ChooserBase.ChooseObject(...)；
    若开启 bStartFromMatchingPose，会走 IPoseSearchProvider::Search(...) 用当前播放时刻做更平滑起始点。
  2. FAnimNode_ChooserPlayer::UpdateAssetPlayer(...)
    控制评估频率（每帧 / 循环点 / 成为 relevant），并在需要时 BlendTo(...) 新资产。

这两层配合起来，才是“上下文先选空间、再平滑播放”的完整策略。

最小验证（切库稳定性版）

  1. 让 Chooser 的边界条件在阈值附近来回摆动（例如速度边界）。
  2. 观察 EvaluateChooser 输出是否高频在两行之间来回切。
  3. 加入滞回或缓冲后再跑同样输入，比较切库次数。
  4. 最后确认 Motion Matching 的切换事件是否同步下降。

如果这里只降了切库抖动但动作仍抖，问题就回到 Query/Schema 层，不在 Chooser。

最后

把选库策略放进 Chooser 后，Motion Matching 才更像可扩展系统而非单点技巧。
最后一篇会把性能、稳定性和排障流程合并成实战清单。
