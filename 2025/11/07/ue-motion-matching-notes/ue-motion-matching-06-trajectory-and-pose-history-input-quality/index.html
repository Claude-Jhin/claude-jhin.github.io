系列定位：UE5 Motion Matching 源码深挖（5.4/5.5）
本文主题：输入构造与稳定性分析

写在前面

很多“匹配不自然”的问题，根因并不在 Database，而在输入：
预测轨迹噪声、历史采样不稳、控制旋转抖动都会直接污染查询向量。

先把结论写明白

Motion Matching 的结果质量上限，首先由 Query 质量决定。
如果输入不稳定，系统只会稳定地“选错更像的结果”。

主线图（输入影响路径）

工程里最常见的真实情况

“库很全但不好看”的第一嫌疑通常不是数据库，而是 Query 输入质量。
因为 Motion Matching 本质是在做“给定 Query 的最优检索”，Query 脏了就只能稳定地选到“脏输入下的最优解”。

Trajectory：它不是速度采样，而是短时意图建模

Trajectory 的价值不在“记录当前速度”，而在“表达角色准备怎么走”。

常见输入来源包括：

  • 当前速度与加速度
  • 朝向与控制器旋转变化
  • 移动模式（地面/空中）相关约束

如果控制输入抖动、Yaw 更新不稳，Trajectory 会直接噪声化，后续评分自然抖动。

Pose History：它是连续性锚点

Pose History 提供“角色刚刚在做什么”的历史上下文。
它帮助系统避免每帧都只看当前瞬时输入而忽略动作惯性。

历史信息不足或采样不稳时，常见现象是：

  • 速度变化时脚步不连贯
  • 转向瞬间上半身或脚部出现不自然跳变

两类典型故障图谱

故障 A：不跟脚（输入过噪）

表现：

  • 小幅摇杆扰动触发频繁候选变化
  • 急停场景中出现“左右试探式”抖动

常见根因：

  • 轨迹预测输入未做足够平滑
  • 选库上下文在边界条件反复横跳

故障 B：迟滞（输入过稳或预测过短）

表现：

  • 方向已经改变，但姿态响应慢半拍
  • 急转时先拖一步再跟上

常见根因：

  • 预测信息权重不足
  • 历史影响过强，系统过度保守

一个好用的输入调试法：先看 Query 曲线，再看动画

很多人上来就盯角色表现，效率很低。
建议先把 Query 输入可视化（至少看方向、速度、预测点变化）：

  1. Query 曲线平稳但动画怪：再看 Schema 与候选空间。
  2. Query 曲线本身就抖：先修输入链路。

这能快速把问题从“视觉层”回溯到“数据层”。

我建议这样做对照

  1. 在同一数据库下做两组输入：
    • 原始控制输入
    • 平滑处理后的输入（尤其是朝向变化）
  2. 保持其他参数不变，仅对比 Query 稳定性与切换抖动。
  3. 记录急转场景下的错选率变化。
  4. 再做一组“减弱历史影响”的对照，比较响应速度与连续性取舍。

在同一套数据库下，通常会看到：
输入越稳，切换越可预测，错选率和视觉抖动都会明显下降。

实战建议：把输入链路当独立系统维护

如果项目规模较大，建议把“Trajectory/PoseHistory 输入构造”当独立模块维护，单独做：

  • 日志开关
  • 参数配置版本化
  • 固定场景回归

这样能显著降低“动画同学改库，程序同学改输入，互相甩锅”的情况。

源码落点（UE5.5 输入链）

输入链建议直接看这三层：

  1. AnimNode_PoseSearchHistoryCollector.cpp
    FAnimNode_PoseSearchHistoryCollector_Base::GenerateTrajectory 会调用
    PoseHistory.GenerateTrajectory(...)，并按 TrajectoryHistoryCount / TrajectoryPredictionCount 组织采样窗口。
  2. PoseSearchHistory.cpp
    FPoseHistory::GenerateTrajectory(...) 内部连续调用
    UPoseSearchTrajectoryLibrary::InitTrajectorySamples、UpdateHistory_TransformHistory、UpdatePrediction_SimulateCharacterMovement。
  3. PoseSearchTrajectoryLibrary.cpp
    FPoseSearchTrajectoryData::UpdateData(...) 从 CharacterMovementComponent 提取速度、加速度、摩擦、朝向更新率等输入。

这三层连起来，就是“控制输入 -> 轨迹推断 -> Query 输入”的完整路径。

为什么它会“不跟脚”或“迟滞”（源码视角）

  1. 不跟脚常见于 ControllerYawRate 波动太大，或地面预测参数在边界状态跳变。
  2. 迟滞常见于历史影响偏强，PoseHistory 的惯性延续盖过了短时转向意图。
  3. 还有一类是采样窗口配比不合理：NumPredictionSamples 太少会慢，太多会“预判过头”。

这三类问题都能在上面三层函数里定位到具体来源。

最小验证（输入链路版）

  1. 固定数据库与 Schema，不做任何改动。
  2. 只改 TrajectoryPredictionCount 和 PredictionSamplingInterval，对比急转响应。
  3. 再只改输入平滑（例如控制朝向的滤波），观察 Query 轨迹是否先变稳。
  4. 最后回看动作表现，确认“输入先变好 -> 命中再变好”的顺序。

这能避免“看到动作怪就先改权重”的常见误区。
