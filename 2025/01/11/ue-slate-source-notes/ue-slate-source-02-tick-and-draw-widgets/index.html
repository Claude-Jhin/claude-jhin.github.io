系列定位：UE5 Slate 原理与源码拆解（UE5.7）
本篇只抓一件事：给一帧 Slate 画时间轴。

从一帧开始，不从控件开始

Slate 的一帧很容易被说成“Tick 一下然后画一下”。这话不算错，但太粗了，粗到没法排障。UI 卡顿、输入慢半拍、窗口不刷新，这些现象都得先问：卡在 Tick、ActiveTimer、窗口遍历、Paint，还是 Renderer 提交？

我更喜欢从 FSlateApplication::TickAndDrawWidgets 这个名字很朴素的函数开始读。它不像某些渲染函数那样看起来很“硬核”，但它决定了 Slate 一帧里各阶段怎么排队，也决定了很多刷新节奏问题应该往哪里查。

我会先看这帧有没有被 Slate 接住，再看窗口有没有被绘制。很多“控件没刷新”的问题，其实在控件之前就已经没了后续。

这里特别容易误会

不要把 TickAndDrawWidgets 当成“强制刷新全 UI”。窗口可见性、ActiveTimer、Invalidation、Throttle 都会参与节奏控制；函数进了，不代表所有子树都做了同等工作。

排查刷新问题

  • 先确认当前帧是否真的进入 TickAndDrawWidgets。
  • 卡顿时把 Tick 成本和 DrawWindows 成本拆开看。
  • 窗口不刷新时检查 ActiveTimer 或失效请求是否真的发生。
  • 多窗口问题要看 SWindow 遍历顺序和可见状态。

源码流程框架

  1. 引擎主循环触发 Slate Tick，入口会落到 FSlateApplication::Tick，再进入 TickAndDrawWidgets。
  2. TickAndDrawWidgets 先处理一帧内和 Widget Tick、ActiveTimer、时间推进相关的工作。这里决定 UI 逻辑有没有机会更新。
  3. 如果当前帧允许绘制，DrawWindows 会转到 PrivateDrawWindows。这一步开始从“更新状态”切到“准备绘制”。
  4. PrivateDrawWindows 内部会先做 DrawPrepass。窗口根节点会调用 SWindow::SlatePrepass，再往下走 SWidget::SlatePrepass。
  5. Prepass 结束后，窗口会被 Paint 成 FSlateWindowElementList，写进 FSlateDrawBuffer。
  6. 最后 Renderer->DrawWindows(DrawBuffer) 把这一帧所有窗口的绘制数据交给 Slate Renderer。

几个细节拆开看

Tick 和 Draw 是两段账

TickAndDrawWidgets 这个名字容易让人以为 Tick 和 Draw 是一个动作。实际排障时最好拆开看：Tick 负责状态推进，Draw 负责把当前状态变成绘制列表。Tick 很便宜但 Draw 很贵、或者 Tick 很贵但 Draw 没怎么动，是两类完全不同的问题。

DrawPrepass 是绘制前的布局结账

Prepass 不只是“提前递归一下”。它会沿控件树更新 DesiredSize、属性和可见性相关状态。很多布局异常如果只在 Paint 里查，会发现几何已经错了；真正该回到 Prepass 看是哪一层 DesiredSize 或 LayoutScale 变了。

DrawBuffer 是应用层和渲染层的交接物

PrivateDrawWindows 最终不是直接调用 RHI，而是把窗口绘制结果收进 DrawBuffer。这个缓冲让 Slate 应用层和渲染实现解耦：应用层只关心窗口该画什么，Renderer 再决定怎么批处理和提交。

这一篇最值钱的不是函数名，而是阶段感。以后遇到“UI 没动”，先问它卡在 Tick、窗口绘制还是 Renderer 之前；别一上来就怀疑控件回调。
