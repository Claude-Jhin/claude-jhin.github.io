本文主题：输入事件从平台层进来后，如何被 Slate/UMG 消费
核心问题：为什么会出现“按钮点不到、键盘无响应、焦点乱跳”？

写在前面

“按钮明明在那，为什么点不到”，这类问题我以前也会先查蓝图。
后来踩坑多了才知道，很多锅根本不在蓝图层，而在更早的路由和焦点链。

所以这篇从 SlateApplication 入口开始走，
目标是把输入问题从“感觉”变成“可复现的调用链”。

我常用的断点走法

  1. 在 ProcessMouseButtonDownEvent 下断，确认事件已进入 Slate 层。
  2. 观察目标 WidgetPath，确认命中的是不是你想要的控件。
  3. 在目标控件输入回调下断，检查 FReply 返回值。
  4. 在 SetUserFocus 下断，确认焦点是否被中途改写。

先看这一段源码

这里要建立的心智模型很简单：

  1. Handled 表示到此消费，后续路由会变化。
  2. Unhandled 表示继续冒泡或交由其他层处理。
  3. 焦点迁移与输入处理不是两套系统，而是同一轮事件处理中的联动结果。

最小复现实验（含反证）

实验 A：验证 FReply 对行为分叉的影响

  1. 自定义一个按钮控件，覆写鼠标按下回调。
  2. 第一轮返回 Handled，第二轮返回 Unhandled。
  3. 对比父容器是否收到事件、焦点是否变化。

预期：

  1. 返回 Handled 时，父层不应再收到同一事件链中的等价处理。
  2. 返回 Unhandled 时，事件可继续冒泡。

反证：
若“Handled 和 Unhandled 没区别”成立，则两轮行为不应发生差异。

我在项目里反复见到的 3 个坑

坑 1：UI 收不到输入一定是蓝图绑定错了

  • 根因：很多问题发生在更前面的 HitTest/路由阶段。
  • 修正：先证明确实命中了目标 WidgetPath，再谈控件逻辑。

坑 2：焦点问题只看 SetKeyboardFocus 就够

  • 根因：忽略了鼠标/手柄事件处理中对焦点的隐式迁移。
  • 修正：把焦点断点放在 SetUserFocus 主路径，而不是只盯业务节点。

坑 3：任意控件都返回 Handled 更安全

  • 根因：过度消费输入导致上层无法接管，交互链断裂。
  • 修正：只有真正处理完且不希望上行时才 Handled，否则应 Unhandled。

现场排查顺序

  1. 事件是否进入 SlateApplication。
  2. 路由命中的 WidgetPath 是否正确。
  3. 目标控件回调是否被调用。
  4. FReply 返回值是否符合预期。
  5. 焦点是否被后续逻辑二次改写。

这一篇要带走什么

输入问题的正确拆法是：
事件入口 -> 命中路径 -> 回调返回值 -> 焦点迁移。
用这四层排查，能把 80% “UMG 输入玄学问题”变成可复现、可解释的问题。
