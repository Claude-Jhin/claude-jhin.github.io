系列定位：UE5 Slate 原理与源码拆解（UE5.7）
本篇只抓一件事：把编辑器 UI 读成命令、菜单和停靠系统的组合。

编辑器 UI 不是一棵手写树

写编辑器扩展时，如果只会 SNew，很快就会撞墙。菜单、工具栏、快捷键、可停靠 Tab、布局恢复，这些东西不是手写一棵巨大的 Slate 树解决的。UE 编辑器把它们拆成 Commands、MultiBox、Docking 和 TabManager，这也是插件能优雅插进去的原因。

这一篇不讲某个编辑器面板怎么摆，而是读编辑器 Slate 的组织方式。FUICommandList 负责动作语义，MultiBox 负责把动作变成菜单/工具栏，FTabManager 和 Docking 系统负责工作区结构。

编辑器 Slate 的味道和运行时 UI 不太一样。它关心的不是某个控件怎么画，而是命令、菜单、布局和停靠怎么让插件有地方接入。

别把扩展写成孤岛

不要把编辑器扩展写成孤立窗口。只要它需要菜单、快捷键或可停靠面板，就应该接入 Commands、MultiBox 和 TabManager，而不是自己拼一套半成品。

菜单、快捷键、Tab

  • 菜单项灰掉先查 CanExecuteAction。
  • 快捷键不触发检查 CommandList 是否在当前上下文。
  • Tab 恢复失败检查 Spawner 名字和 Layout 版本。
  • 停靠异常时追 SDockingNode 树和持久化布局。

源码流程框架

  1. 插件或模块启动时注册 TCommands，生成一组 FUICommandInfo，里面包含显示文本、图标、快捷键等元信息。
  2. 具体上下文创建 FUICommandList，用 MapAction 把命令映射到 Execute / CanExecute / IsChecked 等回调。
  3. 菜单和工具栏扩展用 FMultiBoxBuilder 或 ToolMenus 把 CommandInfo 变成可见条目。
  4. 面板入口通过 FTabManager::RegisterTabSpawner 注册，点击菜单时 Spawn 对应 SDockTab。
  5. Docking 系统用 SDockingArea、SDockingTabStack、SDockingSplitter 维护停靠树。
  6. 布局持久化时，Tab Id 和 Layout 版本必须稳定，否则恢复布局会失败或生成空面板。

几个细节拆开看

CommandInfo 和 CommandList 分开是有用的

FUICommandInfo 描述“这个动作是什么”，FUICommandList 描述“当前上下文里这个动作怎么执行”。同一个命令在不同编辑器面板里可以绑定不同执行逻辑，这就是分层的价值。

MultiBox 不是简单 AddButton

菜单项灰掉、勾选状态、快捷键显示，都来自 CommandList 的状态查询。看菜单问题时，不能只看 AddMenuEntry，还要看当前 UI 命令列表有没有被正确推到上下文里。

Tab 恢复依赖稳定标识

FTabManager 不是靠控件实例恢复布局，而是靠注册的 Spawner 和布局描述。改了 Tab Id、插件加载时机不对、Spawner 没注册，都会让保存过的布局恢复失败。

编辑器这层先到这里

编辑器 UI 这层先不继续铺开。只要记住 Commands、MultiBox、TabManager 这三块，插件扩展就不容易写成孤立的一坨 Slate。
