系列定位：UE5 Slate 原理与源码拆解（UE5.7）
本篇只抓一件事：把“感觉 UI 卡”变成可复现的排障流程。

性能别靠感觉

性能优化最怕“感觉”。今天觉得列表卡，明天觉得菜单慢，改完之后只剩一句“好像快了”。Slate 其实给了不少工具，问题是我们得先固定复现，再用统计和调试器把瓶颈拆到具体阶段。

这一篇把 Stat Slate、Widget Reflector 和 ConsoleSlateDebugger 串起来。我的目标不是罗列工具按钮，而是形成一个可以重复执行的流程：定场景、定阶段、定子树、定失效理由，最后留下回归基线。

这篇没有什么神秘技巧，反而是最笨的：固定场景、固定数据、固定窗口，然后一项一项看。UI 性能优化不怕笨，怕每次都换条件。

这篇只谈证据链

源码按 C:\Epic\UE_5.7 来。这里更看重调用位置和职责边界，不看重精确行号；如果你用 5.5，对着符号搜会比对着行号找靠谱。

我会按这个顺序采样

调试工具入口

源码位置 关键符号 备注

别先优化控件数量

不要一上来优化控件数量。先判断瓶颈是 Prepass、Tick、Paint、Batch、文本塑形还是 RHI 提交；阶段不同，药方完全不同。

做回归时

  • 固定窗口尺寸、DPI、数据量和输入路径后再采样。
  • 每次只改一个变量，保留优化前后统计。
  • 列表问题同时记录条目数、可见条目数和复用命中率。
  • 把 ConsoleSlateDebugger 输出写进回归说明，不只写主观体验。

源码流程框架

  1. 先固定复现场景：窗口尺寸、DPI、数据量、输入操作、打开的面板都不要变。
  2. 用 Stat Slate 或 Insights 先看大类成本：Tick、Prepass、Paint、Batch、Rendering 哪块高。
  3. 用 Widget Reflector 看控件树、命中路径、可见性、Paint 信息，定位具体子树。
  4. 用 ConsoleSlateDebugger 的 Invalidate / Paint / Prepass 通道观察失效原因和绘制频率。
  5. 如果是文本，补看 FontCache / TextLayout；如果是绘制，补看 ElementBatcher 和 RenderBatch；如果是布局，补看 DesiredSize 抖动。
  6. 修改后用同一场景采样，记录前后指标，形成回归基线。

几个细节拆开看

先定阶段，再定控件

性能问题一上来就找“哪个控件慢”很容易错。Slate 的阶段成本差异很大：Prepass 高说明布局或属性变化多，Paint 高说明绘制树重，Batch/RHI 高说明资源状态或提交多。阶段错了，优化方向就错了。

Widget Reflector 看的是证据

Reflector 不只是看树结构。命中路径、可见性、几何、绘制次数都能提供证据。比如目标控件根本不在命中路径里，就不要继续改它的 OnMouseButtonDown。

回归基线要写得土一点

我更愿意记录“1000 条数据、窗口 1920x1080、DPI 1.25、滚动 5 秒、Paint 从 X 到 Y”这种土指标。它不漂亮，但下次有人改坏 UI，你能复现。

把“卡”落成数字

性能诊断这篇故意写得笨一点。Slate 优化最后拼的不是灵感，是同一场景下前后两份能对上的数字。

最后一篇做工程收束：回到自定义控件，把布局、输入、绘制、失效、资源和调试全部装进一套能落地的写法里。
