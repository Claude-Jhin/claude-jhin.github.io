先拆角色

UGameFeatureData 本质上是“功能清单资产”，其中最关键的是 Actions 数组。
UGameFeatureAction 是“清单项执行器”，在激活和停用阶段分别执行行为。

如果把状态机看作“调度层”，那么 Data/Action 就是“业务执行层”。

顺序控制的核心观点

Action 默认按数组顺序执行。
这不是“实现细节”，而是架构约束：

  1. 先注入依赖对象，再绑定输入/UI/能力。
  2. 停用时必须考虑反向收敛，不要让后续 Action 依赖前置 Action 的残留状态。
  3. 如果需要跨 Action 协同，优先通过显式数据与上下文，而不是隐式全局单例。

上下文过滤为什么关键

FGameFeatureStateChangeContext 决定了 Action 是否作用于当前 World。
多人、多 PIE、Server/Client 混合场景里，这一步是防止“误作用域”的第一道保险。

Lyra 最小复现（实验 4）

目标：验证 Action 顺序和停用收敛。

  1. 在同一个 GameFeatureData 放入两个 Action：
    ActionA 注入组件，ActionB 读取组件并注册扩展事件。
  2. 先按 A -> B 执行，确认可用。
  3. 调换为 B -> A，观察激活阶段是否出现空引用或延迟可用问题。
  4. 从 Active -> Loaded，确认 B 的解绑与 A 的移除顺序不会留下脏状态。

这个实验可以快速暴露“看似可用、停用就坏”的设计问题。

常见坑与检查项

  1. 把 Action 当成无序列表使用，结果依赖关系写在注释里而不写在结构里。
  2. 停用阶段只删对象，不做事件解绑，导致二次激活重复注册。
  3. 忽略上下文过滤，在 PIE 多世界下出现“本地生效、联机错乱”的假象。

原理下钻：Action 生命周期不只 Activating/Deactivating

很多人只关心 OnGameFeatureActivating/Deactivating，但在 UE5.5 里 Action 还有注册、加载、卸载等阶段回调路径。
如果你写的是复杂 Action（带缓存、句柄、异步任务），必须明确每个阶段该做什么。

执行顺序与失败策略

建议你在长文里明确写出两条规则：

  1. 正向执行按 Actions 顺序，反向停用必须保证依赖后置项先收敛。
  2. 对每个 Action 定义失败级别：硬失败（中断激活）/软失败（记录并降级）。

如果不提前定义失败级别，线上会出现“一个可忽略 UI 错误拖垮整个 Feature 激活”的问题。

上下文语义：多世界下的决定性边界

FGameFeatureStateChangeContext 不是附属参数，它是执行许可。
建议在 Action 实现里做到：

  1. 先判断上下文是否适用于当前 WorldContext。
  2. 只在通过时执行副作用逻辑。
  3. 记录上下文键值用于回收阶段配对。

调试策略（建议）

  1. 断在 OnGameFeatureActivating，看 Action 实际执行顺序是否符合预期。
  2. 断在 CallbackObservers，确认观察者是否改变了生命周期行为。
  3. 激活与停用都抓一份“句柄集合快照”，验证有没有泄漏。

进阶练习

为一个复杂 Feature 写三种 Action：

  1. 数据注册类 Action
  2. 世界注入类 Action
  3. 表现层 Action

然后故意让第 3 个 Action 失败，观察状态机是否能安全回到可恢复状态，以及前两个 Action 是否需要手动补偿。

本篇结论

GameFeatureData 是声明，Action 是执行，Context 是边界。
下一篇我们进入最常用的执行器：AddComponents 与 ModularGameplay 的桥接主线。

为什么这一篇是“工程分水岭”

前面几篇更多是系统框架。
到了 Data/Action 这一层，你开始真正面对项目复杂度：

  1. 执行顺序怎么定。
  2. 失败怎么回滚。
  3. 多世界怎么隔离。
  4. 重复激活怎么保持幂等。

这些问题一旦处理不好，Feature 再漂亮也会在联调和上线阶段失控。

Action 编排的实用规则（不是教条）

我在项目里会强制三条规则：

  1. 先基础再表现：先注册数据/组件，再挂 UI/输入。
  2. 有状态就要有句柄：凡是会“新增”的动作，必须能“按来源撤销”。
  3. 动作只做一件事：一个 Action 不要同时做输入、UI、能力三种注入。

这么做的好处是，排障时能快速定位“到底是哪一段没收敛”。

生命周期表（建议放正文）

阶段 该做什么 不该做什么
Registering 注册轻量元信息、准备句柄容器 直接触发重副作用逻辑
Loading 读取/校验数据资产 启动依赖世界对象的逻辑
Activating 注入运行时行为 隐式跨世界共享状态
Deactivating 逆序回收、解绑事件 只做“删对象”不做“撤引用”
Unregistering 清理残留缓存 再次新增运行时对象

有了这张表，团队成员做 Action 时很少再“把阶段写反”。

断点剧本：定位“重复激活后越跑越乱”

  1. 断在 OnGameFeatureActivating，记录每个 Action 实际调用次数。
  2. 断在 OnGameFeatureDeactivating，核对是否一一回收。
  3. 观察 ContextHandles 或等价容器是否持续增长。
  4. 做三轮“激活-停用-激活”循环，确认无残留。

如果第三轮开始出现异常，通常就是回收不对称或上下文配对失效。

进阶练习：写一个“故意失败”的 Action

练习目标是验证回滚链路，而不是验证 happy path。

  1. 在激活中段故意返回失败或抛出可控错误。
  2. 观察前序 Action 是否安全回收。
  3. 再次激活同一 Feature，确认状态可恢复。

这比单纯写成功路径更能锻炼团队的上线稳定性思维。

附录：Action 代码评审清单

建议你把下面这份清单直接放进 Code Review 模板：

  1. 这个 Action 只做一件事吗？
  2. 激活新增的对象/句柄是否全部可回收？
  3. 停用逻辑是否考虑了部分激活失败场景？
  4. 是否正确使用了世界上下文过滤？
  5. 是否有跨 Feature 的隐式依赖？
  6. 是否在日志里留下足够的排障信息？

如果其中任意两项答不上来，建议先不要合并。
这条规则看起来严格，但能显著减少“联调时才发现难以回收”的问题。
