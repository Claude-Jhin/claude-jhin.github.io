本文主题：长列表为什么会“滚动一卡一卡”、内存忽高忽低
核心问题：ListView 什么时候会复用条目，FUserWidgetPool 什么时候真正生效？

写在前面

长列表优化这件事，很多时候不是“渲染不行”，而是“更新策略太粗”。
我第一次在背包系统里压 5000 条数据时，滚动卡顿就是这么来的。

这篇会把 ListViewBase、SListView 和 FUserWidgetPool 的协作关系讲透，
重点放在“什么时候该复用，什么时候你在悄悄重建”。

我常用的断点走法

  1. 在 RebuildListWidget 下断，确认自定义列表是否正确构造 Slate 列表。
  2. 在 RegenerateAllEntries 下断，观察是否频繁全量重生成。
  3. 在 GetOrCreateInstance 下断，确认是否发生复用而非反复创建。
  4. 在 OnEntryReleased 与 OnListItemObjectSet 观察条目回收/重绑节奏。

要点：

  1. 池化的是 UUserWidget + 对应 Slate 缓存关系，不只是一个 UObject 指针。
  2. 频繁 RegenerateAllEntries 会冲掉复用收益。
  3. 条目更新应偏向“数据重绑”，而不是“重建条目树”。

最小复现实验（含反证）

实验 A：5000 条数据滚动压测

  1. 生成 5000 条数据对象，列表只显示可视窗口。
  2. A 方案：每次筛选都 RegenerateAllEntries。B 方案：增量更新数据并触发局部刷新。
  3. 记录滚动帧时间、GC 峰值、创建条目次数。

预期：
增量方案在滚动稳定性和创建次数上显著优于全量重建方案。

反证：
若“全量重建影响不大”成立，则两方案的条目创建数和 GC 峰值应接近。

我在项目里反复见到的 3 个坑

坑 1：ListView 卡顿一定是 Slate 慢

  • 根因：常见瓶颈在业务层频繁全量刷新。
  • 修正：优先审计 RegenerateAllEntries 触发频率。

坑 2：池化开启后就不会再触发 Construct/Destruct

  • 根因：Slate 资源释放策略会影响 NativeConstruct/NativeDestruct 触发。
  • 修正：把条目逻辑设计为可重入，避免依赖“只构造一次”。

坑 3：条目 UI 状态可永久驻留在 Widget 内

  • 根因：复用时条目会绑定不同数据对象，旧状态污染新项。
  • 修正：在 OnListItemObjectSet 完整重置状态，释放时清理临时态。

现场排查顺序

  1. 统计每次交互是否触发了全量 RegenerateAllEntries。
  2. 统计条目创建/复用比例。
  3. 检查条目重绑时是否遗漏状态重置。
  4. 检查是否过度释放 Slate 资源导致重复构建。
  5. 检查数据对象是否符合 IUserObjectListEntry 使用约束。

这一篇要带走什么

高密度列表优化的本质是“减少重建、提高复用、稳定重绑”。
先把 ListViewBase -> Pool -> Entry 生命周期 这条链读通，再做样式层优化，收益最大。
