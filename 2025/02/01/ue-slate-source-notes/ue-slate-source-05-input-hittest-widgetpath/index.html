系列定位：UE5 Slate 原理与源码拆解（UE5.7）
本篇只抓一件事：把“按钮没响应”还原成命中链路问题。

按钮没响，不一定是按钮的问题

春节这篇本来想写轻一点，结果 Slate 输入链路一点都不轻。一个按钮点不动，最不该做的事就是先怀疑按钮。事件到按钮之前，已经经过平台消息、窗口定位、HittestGrid、WidgetPath 和路由策略，按钮只是最后一个接电话的人。

这一篇只追“事件怎么找到控件”。我会把 ProcessMouseButtonDownEvent 当入口，顺着窗口命中、路径构建和路由往下看。只要这条路清楚，焦点、捕获、拖拽那些后续问题才有地方安放。

输入链路很像查快递：最后没送到，不代表收件人有问题。先看它经过了哪个窗口、哪条路径、哪个 HitTest 结果。

可见不等于可点

不要以为“看得见”就“点得到”。HitTestInvisible 和 SelfHitTestInvisible 这种可见性状态会让绘制和命中分家；UI 在屏幕上，不代表它在输入路径上。

查输入我会这么做

  • 输入不到先查 Visibility，而不是先改回调。
  • 用 Widget Reflector 看命中路径是否包含目标控件。
  • 拖拽或捕获状态下检查 MouseCaptor 是否改写目标。
  • 多用户输入要看 UserIndex 和焦点用户。

源码流程框架

  1. 平台层把鼠标事件交给 FSlateApplication::ProcessMouseButtonDownEvent，事件里带 PlatformWindow、屏幕位置、用户索引等信息。
  2. Slate 先定位事件对应的窗口，必要时结合鼠标捕获状态改写目标路径。
  3. 没有捕获时，会根据鼠标位置和上一帧绘制建立的 FHittestGrid 找到 WidgetsUnderCursor。
  4. 命中结果会组织成 FWidgetPath：从顶层窗口到最里层目标控件的一条路径。
  5. RoutePointerDownEvent 会沿路径做 Preview / Bubble 一类路由，让父子控件都有机会处理事件。
  6. 控件返回的 FReply 不在这里结束，还会交给 ProcessReply 执行焦点、捕获等副作用。

几个细节拆开看

HittestGrid 来自绘制期

这点很关键：命中测试不是输入时现算一遍完整布局，而是大量依赖绘制/布局阶段留下的数据。上一帧没有进入 HittestGrid 的控件，这一帧自然点不到。Visibility、裁剪、Layer 都可能影响它。

WidgetPath 是事件路由的证据

查输入问题时，FWidgetPath 比单个控件回调更有价值。路径里没有目标控件，就说明问题发生在命中之前；路径里有目标但回调没进，再看可见性、Enabled、Preview 或父控件是否提前 Handled。

鼠标捕获会绕开普通命中

拖拽、滑块、窗口拖动时，后续事件可能直接送给 Captor，而不是重新根据鼠标位置命中。很多“鼠标明明移到外面了还在响应”的问题，其实是捕获状态没释放。

先把事件找到谁讲清楚

输入先讲到“找到谁”。只要 FWidgetPath 这条路清楚了，后面的焦点、捕获、拖拽就不再是散点问题。
