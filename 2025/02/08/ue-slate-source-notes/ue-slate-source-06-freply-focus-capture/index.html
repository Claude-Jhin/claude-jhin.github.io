系列定位：UE5 Slate 原理与源码拆解（UE5.7）
本篇只抓一件事：把 FReply 从返回值读成一包 UI 意图。

Reply 不是一句“处理了”

FReply 是 Slate 里一个很容易被轻视的类型。它长得像“我处理了/我没处理”的返回值，但它其实能改焦点、抓鼠标、发起拖拽、触发导航。很多焦点灾难不是从焦点函数开始的，而是从某个控件返回了一份带副作用的 Reply 开始的。

这一篇不把 FReply 当布尔值读。我要看它如何在事件路由结束后，被 FSlateApplication 拿去执行那些延迟副作用。理解这一层，才能解释为什么一个小小的 Handled() 会让后续输入路径全变了。

FReply 最危险的地方在于它太像返回值。实际它更像一张小纸条：事件路由结束后，应用层照着纸条去改焦点、捕获和导航。

Reply 落地路径

我会翻这几处

源码位置 关键符号 备注
SlateCore/Private/Input/Reply.cpp FReply 输入回复对象实现
Slate/Private/Framework/Application/SlateApplication.cpp ProcessReply 执行 Reply 副作用
Slate/Private/Framework/Application/SlateUser.cpp FSlateUser 焦点与捕获状态
Slate/Private/Framework/Application/NavigationConfig.cpp FNavigationConfig 导航规则

Handled 不是 true

不要把 FReply::Handled 翻译成 C++ 里的 return true。它可能还带着 CaptureMouse、SetUserFocus、BeginDragDrop 等命令；真正效果要等应用层处理 Reply 才落地。

焦点乱时

  • 焦点乱跳时全局搜 SetUserFocus，别只看 OnFocusReceived。
  • 鼠标松开不到控件时检查是否被 CaptureMouse 接管。
  • 事件被吞时找路由上第一个返回 Handled 的控件。
  • 手柄导航异常要同时看 NavigationConfig 和控件可聚焦性。

源码流程框架

  1. 控件事件函数返回 FReply，最基本的是 Handled() 或 Unhandled()。
  2. 路由器根据 Handled/Unhandled 决定事件是否继续冒泡或交给其他控件。
  3. 如果 Reply 里设置了 SetUserFocus、CaptureMouse、ReleaseMouseCapture、BeginDragDrop 等操作，它们只是被记录下来。
  4. 路由结束后，FSlateApplication::ProcessReply 统一读取这些操作，并修改 FSlateUser、MouseCaptor、DragDropContent 等全局状态。
  5. 焦点变化会影响后续键盘事件路由；鼠标捕获会影响后续鼠标事件目标。
  6. Navigation Reply 会进入导航逻辑，结合 FNavigationConfig 和当前路径寻找下一个焦点控件。

几个细节拆开看

Reply 是延迟执行的命令包

FReply::Handled().SetUserFocus(...) 不是当场改焦点，而是把意图塞进 Reply。真正执行点在 ProcessReply。所以查焦点问题时，断在 OnMouseButtonDown 只能看到谁提出请求，断在 ProcessReply 才能看到请求怎么落地。

Handled 的影响比想象大

Handled 会改变路由结果，也可能阻止更外层控件收到事件。编辑器扩展里常见问题是内层控件为了拦截点击返回 Handled，结果外层菜单或窗口逻辑拿不到本该拿到的输入。

焦点按 User 分开维护

多用户、多手柄、多 PIE 窗口场景不要把焦点当成一个全局变量。FSlateUser 持有用户级状态，UserIndex 错了，焦点看起来就像随机跳。

这里先收住

FReply 这一层读完，很多焦点问题会变得没那么邪门：不是 Slate 随机换目标，而是某个 Reply 明确要求它换。
