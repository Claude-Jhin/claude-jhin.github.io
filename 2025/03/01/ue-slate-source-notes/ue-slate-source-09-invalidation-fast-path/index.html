本篇只抓一件事：把 Invalidation 当成复用协议，而不是性能开关。

Invalidation 不负责变魔术

Invalidation 是 Slate 里最像“玄学按钮”的东西。打开之后有时立竿见影，有时反而更慢。问题不在它玄学，而在我们经常忘了问：这棵子树稳定吗？失效理由准确吗？缓存命中率够吗？

这一篇读 FSlateInvalidationRoot 和 WidgetProxy。我想把 Invalidation 从“能优化 UI”这种口号，拆成一套很朴素的判断：哪些布局、绘制、命中数据还能复用，哪些必须重算。

Invalidation 好用的时候很爽，不好用的时候很迷惑。我的经验是先问子树稳不稳，再问缓存值不值；顺序反了，就容易把优化写成负优化。

缓存不是免费午餐

不要把 Invalidation 当成“打开就快”。如果控件每帧变、子节点顺序频繁改、文本反复重排，缓存系统只是在更认真地帮你收拾烂摊子。

查失效抖动

  • 先判断子树是否稳定，再谈 Invalidation 收益。
  • 频繁失效时统计失效理由，重点看 ChildOrder 和 Volatility。
  • 命中异常时检查 HittestGrid 是否和 WidgetProxy 同步。
  • 不要在 Tick 里无脑 InvalidateLayoutAndVolatility。

源码流程框架

  1. 控件状态变化调用 Invalidate，带上 EInvalidateWidgetReason，比如 Layout、Paint、Volatility、ChildOrder。
  2. 失效会向上找到对应的 Invalidation Root，根会记录哪些 Widget 或 Proxy 需要更新。
  3. FSlateInvalidationRoot::PaintInvalidationRoot 是快速路径绘制的核心入口，它决定哪些部分复用缓存、哪些部分重算。
  4. FWidgetProxy 保存控件在快速路径中的排序、可见性、父子关系、几何、Layer 等摘要信息。
  5. 如果只是 Paint 失效，布局可能复用；如果是 Layout 或 ChildOrder 失效，Prepass、排序、HittestGrid 都可能被迫更新。
  6. 绘制结果可进入 FSlateCachedElementData，下一帧如果条件满足就复用。

几个细节拆开看

失效理由决定重算范围

这是 Invalidation 最核心的细节。Paint 失效和 Layout 失效不是一个成本级别；ChildOrder 更重，因为它会影响 WidgetList 顺序、命中测试、绘制层级。乱用 InvalidateLayoutAndVolatility 等于告诉 Slate “你多重算一点吧”。

WidgetProxy 是快速路径的影子节点

快速路径不想每次都重新沿真实控件树做全量工作，所以需要 Proxy 保存排序、父子、可见性等信息。问题是影子必须和真身同步；同步不准，就会出现缓存绘制正确但命中或层级不对的怪问题。

Volatile 是主动放弃部分缓存

高频动画、光标、拖拽装饰这类控件如果每帧都变，硬缓存意义不大。Volatile 的意义不是“这个控件性能差”，而是告诉失效系统：别假装它稳定。

别把缓存当信仰

Invalidation 先收成一句土话：稳定的东西才值得缓存。不稳定的东西硬塞进缓存体系，只会让调试多一层烟。
