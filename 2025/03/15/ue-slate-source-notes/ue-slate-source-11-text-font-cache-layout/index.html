文本的成本不只在画字

中文文本卡顿特别容易被一句“字体贴图太大”糊弄过去。字体图集当然重要，但文本真正麻烦的地方在于测量、塑形、换行、Run 布局和缓存失效。你在 Paint 里看到的是结果，贵的活可能前面已经干完了。

这一篇从 FSlateFontCache、FSlateTextShaper 和 FTextLayout 三块读文本。我的目标不是写一篇排版学，而是找到中文、富文本、长列表这三类场景为什么容易让 Slate 变重。

中文 UI 卡顿不要急着甩锅给字体贴图。字形缓存是一块，塑形、换行、Run 重建也是一块；后几块经常更隐蔽。

别只盯 OnPaint

不要把文本性能只归因于 OnPaint。内容变化会提前触发布局和塑形，OnPaint 只是把结果变成 DrawElement；真正的成本可能根本不在你下断点的地方。

中文和富文本

  • 长列表文本优先减少每帧内容变化。
  • 中文混排场景观察 FontCache miss 和 shaped sequence 重建。
  • 富文本卡顿时检查 Run 是否频繁重建。
  • 字体丢字时确认 CompositeFont 和 fallback 链路。

源码流程框架

  1. STextBlock 或富文本控件的文本属性变化后，会触发 TextLayout 更新或缓存失效。
  2. FTextLayout 负责组织 Line、Run、Wrapping、Justification 等布局结果。
  3. 测量阶段会通过 FSlateFontMeasure 查询字符串尺寸，内部依赖字体信息和 shaped glyph。
  4. 复杂文本会进入 FSlateTextShaper，结合 HarfBuzz 做 glyph shaping，中文混排、emoji、fallback 都可能走更复杂路径。
  5. FSlateFontCache 保存字体、字形和 atlas 相关数据；glyph 缺失时会生成并更新缓存。
  6. Paint 阶段的 MakeText / MakeShapedText 只是把已准备好的文本绘制描述交给 ElementBatcher。

几个细节拆开看

文本变化比绘制更贵

频繁 SetText 的长列表很容易卡，不只是因为每帧多画几个字，而是 TextLayout、测量、塑形缓存可能都被打掉。能不变就不变，能复用 Run 就复用，这是文本 UI 的第一条优化。

中文问题常在 fallback 和 shaping

中文、英文、数字、图标字体混排时，字体 fallback 链会频繁参与。一个字符串里不同字形可能来自不同字体资源，最后不只是测量变复杂，批处理资源也可能变复杂。

FontCache miss 是关键观察点

如果性能尖峰伴随 glyph 生成或 atlas 更新，那优化方向就不是减少控件，而是预热字体、减少动态文本范围、控制字号和字体组合。

文本系统先记住这个分层：内容变化、布局重建、塑形、字体缓存、绘制元素。卡顿在哪层，优化手段完全不同。
