系列定位：UE5 Motion Matching 源码深挖（5.4/5.5）
本文主题：系统级拆解 Motion Matching 的模块协作关系

写在前面

如果一上来就钻 FAnimNode_MotionMatching，很容易只看见“节点在切动画”，却不知道输入从哪来、数据库怎么选、上下文怎么切。
所以第二篇先做全局图，把模块关系和数据流一次串起来。

先把图景搭起来

Motion Matching 体系可以抽象成四层：

  1. 输入层：Trajectory / Pose History 提供查询信息。
  2. 检索层：PoseSearch Schema + Database 定义并检索特征。
  3. 决策层：Chooser 决定当前用哪组数据库与策略。
  4. 输出层：AnimGraph 节点完成姿态切换与混合输出。

主线图（系统数据流）

先把模块边界说清楚

1. PoseSearch：检索框架本体

PoseSearch 负责两件核心工作：

  1. 用 UPoseSearchSchema 定义特征空间（采什么、怎么拼、权重多少）。
  2. 用 UPoseSearchDatabase 保存离线索引，在运行时做候选评分。

它不负责“玩法语义”，只负责“在给定候选空间内找最匹配姿态”。

2. Trajectory / Pose History：查询输入提供者

Motion Matching 不是“看当前速度就切动作”，它需要时间维度信息：

  • 过去一段时间角色姿态/运动历史（History）。
  • 未来一段时间输入意图预测（Prediction）。

这部分输入决定了 Query 的稳定性上限。输入抖动，结果就会抖动。

3. Chooser：上下文决策层

Chooser 不负责“挑帧”，它负责“挑搜索空间”。
例如：

  • 空手移动用 A 库
  • 持枪移动用 B 库
  • 受伤状态再切 C 库

它让“业务条件”与“检索逻辑”解耦，不用把所有条件塞进 AnimGraph 节点细节里。

4. AnimGraph（FAnimNode_MotionMatching）：运行时执行层

AnimGraph 里的 Motion Matching 节点做的是每帧闭环：

  1. 收集输入。
  2. 构建 Query。
  3. 调用 PoseSearch 检索。
  4. 根据状态与约束决定是否切换。
  5. 输出最终动画姿态并参与混合。

一帧里这些模块如何接力

可以按“谁先做决策”来记：

  1. Chooser 先决定“去哪几个库搜”。
  2. Trajectory/PoseHistory 决定“拿什么去搜”。
  3. PoseSearch 决定“搜出来谁最像”。
  4. FAnimNode_MotionMatching 决定“现在切不切，以及怎么切”。

这四步顺序很关键。很多调试误区都来自把它们混在一起。

常见误判：把选库问题当成匹配问题

经常遇到一种情况：角色“看起来选错动作”。
但根因可能不是评分算法，而是 Chooser 先把它送到了错误数据库。

建议的排查顺序：

  1. 先看当前命中的是哪个 Database。
  2. 再看 Query 本身是否稳定。
  3. 最后再看 Schema 权重和候选评分。

用源码名词建立阅读地图

后续阅读源码时，可以把关注点落到这几个对象：

  • UPoseSearchSchema：特征定义协议。
  • UPoseSearchDatabase：候选数据与索引容器。
  • FAnimNode_MotionMatching：运行时调度核心。
  • FMotionMatchingState：当前检索/切换状态承载体。

你不必一开始就看全实现，先按职责分层就能避免“文件越看越多，但主线越来越散”。

我建议的验证方式

  1. 打开 PoseSearch 与 MotionMatching 相关调试显示。
  2. 在同一移动输入下，分别切换两套 Chooser 条件（例如 Walk 与 Sprint 语境）。
  3. 观察 Database 选择变化、匹配姿态变化和最终步态变化是否一致。
  4. 在不改 Schema 的前提下，仅改 Chooser 条件，验证“选库变化会先于姿态风格变化”。

如果链路是通的，现象会很清楚：
它不是节点在“随机挑动作”，而是先定搜索空间，再在该空间里按查询向量做评分检索。

源码级模块关系表（UE_5.5）

按“输入 -> 检索 -> 决策 -> 输出”映射到本机 C:\Epic，可以直接定位到：

  1. 输入层（Trajectory / History）
    C:\Epic\UE_5.5\Engine\Plugins\Animation\PoseSearch\Source\Runtime\Private\AnimNode_PoseSearchHistoryCollector.cpp
    关键入口：FAnimNode_PoseSearchHistoryCollector_Base::GenerateTrajectory、Update_AnyThread。
  2. 检索层（Schema / Database）
    ...\PoseSearchSchema.cpp 的 UPoseSearchSchema::BuildQuery / Finalize；
    ...\PoseSearchDatabase.cpp 的 UPoseSearchDatabase::Search / SearchContinuingPose。
  3. 决策层（Chooser）
    C:\Epic\UE_5.5\Engine\Plugins\Chooser\Source\Chooser\Private\Chooser.cpp 的 UChooserTable::EvaluateChooser。
  4. 输出层（AnimGraph）
    ...\AnimNode_MotionMatching.cpp 的 FAnimNode_MotionMatching::UpdateAssetPlayer。

一帧真实时序（函数名版）

把“系统协作”翻成一条可断点的路径，大致是：

  1. FAnimNode_PoseSearchHistoryCollector::Update_AnyThread 发布 FPoseHistoryProvider。
  2. FAnimNode_MotionMatching::UpdateAssetPlayer 收集数据库并调用 UPoseSearchLibrary::UpdateMotionMatchingState(...)。
  3. UPoseSearchLibrary::UpdateMotionMatchingState(...) 内部先尝试 SearchContinuingPose，再遍历 Database->Search(...)。
  4. UPoseSearchDatabase::Search(...) 根据 PoseSearchMode 走 BruteForce / VPTree / PCAKDTree 分支。
  5. 若命中新姿态，回到 FAnimNode_MotionMatching::UpdateAssetPlayer 触发 BlendTo(...)。

这条链路对应了我们前面那张图的每一层，而且每一层都能在源码里单独验证。
