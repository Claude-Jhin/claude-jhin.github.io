系列定位：UE5 Motion Matching 源码深挖（5.4/5.5）
本文主题：运行时每帧查询、评分与切换的核心闭环

写在前面

这是本专栏的核心篇。
我们会把“节点每帧到底做了什么”拆成可跟踪的调用主线：输入更新、查询构建、候选评分、切换决策、状态更新。

先把判断放在前面

FAnimNode_MotionMatching 不是直接“播动画”，而是在每帧维护一个搜索状态机：
何时重搜、搜哪些库、如何避免抖动切换、如何保证连续性。

主线图（运行时闭环）

先看核心入口的职责

在源码层面，FAnimNode_MotionMatching 的关键职责可以概括成：

  1. 维护当前匹配状态（当前资产、当前时间、是否需要重搜）。
  2. 在每帧更新中构建 Query。
  3. 在候选数据库中搜索并评估。
  4. 决定继续当前播放还是切换到新候选。
  5. 把结果交给动画输出链路做混合。

它更像“运行时调度器”，不是单纯“播片节点”。

一帧里到底发生了什么

把每帧拆开看，会更好理解参数的作用位置：

阶段 1：输入采样与上下文确定

  • 收集当前移动输入、朝向、速度等。
  • 更新轨迹与姿态历史缓存。
  • 通过 Chooser 或外部逻辑确定当前可搜索数据库集合。

这一阶段常见问题：选库边界抖动，导致还没开始评分就先“上下文震荡”。

阶段 2：构建 Query 向量

根据 UPoseSearchSchema 把当前输入转成统一特征向量。
这个向量必须与数据库索引向量同构，否则评分没有意义。

这一阶段常见问题：输入噪声大，导致 Query 每帧抖动。

阶段 3：候选搜索与评分

在当前数据库中检索候选姿态，并按代价函数排序。
这里得到的“最佳候选”并不必然立刻切换。

这一阶段常见问题：大家只盯“分数最小”，忽略了连续性约束。

阶段 4：切换判定

运行时会综合考虑：

  • 当前结果是否已经足够好
  • 新候选是否显著更优
  • 切换会不会造成突兀

也就是说，系统追求的是“稳定的好结果”，不是“每帧贪心最优”。

阶段 5：状态更新与输出

最终把决策写回 FMotionMatchingState 一类状态容器，并输出姿态到 AnimGraph。
后续再与其他动画层（上半身叠加、Additive、IK 等）共同完成最终结果。

为什么“最佳候选变化”不等于“必须切换”

这是理解 Motion Matching 的关键之一。
如果每帧都切到当前全局最小代价，视觉上常常会抖。

因此运行时通常会有“延续当前解”的策略：

  • 降低不必要切换
  • 保持动作惯性
  • 给短时噪声留缓冲

这也解释了为什么调参时要同时看“分数曲线”和“切换事件”，只看其一很容易误判。

调试时建议同时观测 4 个量

  1. 当前命中的 Database。
  2. 最佳候选分数。
  3. 是否触发切换。
  4. 当前播放片段时间与速度。

这四个量能覆盖“选库 -> 搜索 -> 判定 -> 输出”完整链路。

我建议你这样跟一遍

  1. 在运行时打印或可视化当前选中 Database、最佳候选分数和是否触发切换。
  2. 连续执行“匀速直跑 -> 急转 -> 急停 -> 再加速”。
  3. 观察切换时机是否与分数变化、输入变化一致。
  4. 人为制造一段输入抖动（快速左右小幅摇杆），观察“分数抖动”与“切换抖动”是否同步。

跟下来你会很直观地看到：
切换并不是每帧都触发，系统会在“更优匹配”和“动作连续性”之间做折中。

放到工程里怎么用

当你要优化“看起来不稳”的问题时，优先级建议是：

  1. 先稳输入与选库边界。
  2. 再看 Query 与分数曲线。
  3. 最后看切换阈值与连续性策略。

这样排查通常比直接改权重更快找到根因。

源码调用链（UE5.5 函数名版）

你可以直接在 C:\Epic\UE_5.5 下按这个顺序跟：

  1. AnimNode_MotionMatching.cpp
    FAnimNode_MotionMatching::UpdateAssetPlayer
    这里处理 reset / 调试信息 / 数据库列表，然后调用 UPoseSearchLibrary::UpdateMotionMatchingState(...)。
  2. PoseSearchLibrary.cpp
    UPoseSearchLibrary::UpdateMotionMatchingState(...)
    关键局部变量是 bSearch、bSearchContinuingPose、bJumpToPose。
    流程是：先 SearchContinuingPose，再遍历各库 Database->Search(...) 比最优。
  3. PoseSearchDatabase.cpp
    UPoseSearchDatabase::Search(...)
    根据 PoseSearchMode 分发到 SearchBruteForce / SearchVPTree / SearchPCAKDTree。
  4. 回到 AnimNode_MotionMatching.cpp
    如果 MotionMatchingState.bJumpedToPose，执行 BlendTo(...)，否则延续当前播放并更新速率。

两个常被忽略的运行时细节

  1. 继续姿态搜索不是“兜底”，而是主路径的一部分
    SearchContinuingPose 会带着 ContinuingPoseCostBias 参与同一轮比较，不是单独的后处理。
  2. 多库场景下会考虑 Query 缓存复用
    SearchContext.SetUseCachedChannelData(...) 只在“可能跨 Schema 构建 Query”时才更有价值，避免重复构建代价。

最小验证（断点建议）

  1. 在 FAnimNode_MotionMatching::UpdateAssetPlayer 里观察 DatabasesToSearch 与 NextUpdateInterruptMode。
  2. 在 UPoseSearchLibrary::UpdateMotionMatchingState 里看 bSearchContinuingPose 和最终 bJumpToPose。
  3. 在 UPoseSearchDatabase::Search 里确认当前走的是哪种 PoseSearchMode。
  4. 回到节点侧看 MotionMatchingState.bJumpedToPose 是否与视觉切换一致。

把这 4 个点串起来，运行时就不再是黑盒。
