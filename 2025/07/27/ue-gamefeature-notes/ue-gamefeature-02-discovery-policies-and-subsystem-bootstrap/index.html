先回答一个高频问题

“为什么同一份 GameFeature，在 A 项目自动加载，在 B 项目不加载？”

答案通常不在 GameFeatureData 本身，而在 Project Policies。
UE 在 Subsystem 初始化时，会把“要不要加载、加载客户端还是服务端数据、何时加载”交给策略对象决定。

调用链图

关键函数定位

  1. UGameFeaturesSubsystem 初始化期间会绑定调试命令与策略初始化。
  2. UGameFeaturesProjectPolicies 决定加载模式（Client/Server）。
  3. LoadBuiltInGameFeaturePlugins 负责批量扫描并驱动加载。

这条链路的工程意义

入口链路决定了三件大事：

  1. 哪些插件会被发现并进入候选集。
  2. 哪些环境（Client/DedicatedServer）真正加载对应数据。
  3. 你的项目是否有机会在最前面做“禁用、降级、灰度”。

如果你要做线上热更治理，第一刀应该切在 Policy，而不是在 Action 里打补丁。

Lyra 最小复现（实验 2）

目标：验证“策略优先级高于内容配置”。

  1. 准备两个 GameFeature：GF_CombatCore、GF_EventMode。
  2. 在自定义 Project Policies 里临时过滤 GF_EventMode。
  3. 启动项目后执行 ListGameFeaturePlugins，确认它未进入预期激活路径。
  4. 放开过滤规则，再次启动并比对状态变化。

这个实验可以直接套在 Lyra 项目分支上，效果最直观。

常见坑与检查项

  1. 忽略 GetGameFeatureLoadingMode，导致 Dedicated Server 加载了不需要的 Client 资源。
  2. 把环境差异放在 Action 里硬判断，长期维护成本高。
  3. 缺少统一 ListGameFeaturePlugins 快照，排障时无法证明“到底有没有被加载器看见”。

原理下钻：URL 协议与插件发现不是一件事

很多文章会把“插件发现”写成单一步骤，但在 UE5.5 里至少分两段：

  1. 解析 URL 协议（file: / installbundle:）并提取路径与选项。
  2. 根据策略过滤和当前环境决定是否创建状态机并驱动目标状态。

你可以把它理解成“寻址 + 准入”两层：

  1. 寻址层回答“它是谁、在哪里”。
  2. 准入层回答“现在应不应该让它进入加载流程”。

启动顺序中的关键细节

InitGameFeatureManager() 在策略层执行，这意味着你可以在“任何 Feature 进入状态机之前”统一做项目级治理：

  1. 版本闸门（黑白名单）
  2. 环境闸门（Client/Server）
  3. 灰度闸门（分平台、分构建）

这比在 Action 层做 if/else 更稳定，因为 Action 运行时很多副作用已经发生。

调试策略（推荐断点序列）

  1. 断在 ParsePluginURL，确认 URL 和选项解析是否符合预期。
  2. 断在 GetGameFeatureLoadingMode，确认 Client/Server 加载模式。
  3. 断在 LoadBuiltInGameFeaturePlugins，确认候选集合规模。
  4. 断在 FindOrCreateGameFeaturePluginStateMachine，确认最终准入结果。

如果 1~3 都正确而 4 没被命中，问题通常是策略过滤或插件合法性检查。

本篇结论

GameFeature 的“入口治理”是项目级能力，不是单个插件能力。
下一篇我们进入状态机内核，看 Installed/Registered/Loaded/Active 到底如何被驱动和回滚。

一次真实排障：插件明明在目录里，为什么就是不加载

这类问题在团队里非常高发，排查顺序如果不固定，很容易花一下午还没有结果。
我通常按下面四步查：

  1. URL 是否被正确构造（file: 还是 installbundle:）。
  2. Policy 是否放行（环境、平台、构建配置）。
  3. Descriptor 是否被识别为合法 GameFeature 插件。
  4. 是否真正创建了状态机并开始转移。

只有四步都过了，才值得去看后面的 Action 逻辑。
否则你会在执行层绕圈子，越查越乱。

Policy 设计建议：不要把业务判断写死在 Action 里

更稳妥的实践是把“准入条件”尽量前置到 Policy：

  1. 客户端是否加载某类活动资源。
  2. Dedicated Server 是否跳过纯表现 Feature。
  3. 特定平台是否禁用某组 Feature。

这么做的好处是：

  1. 策略可集中审计。
  2. 线上开关更可控。
  3. 业务 Action 更纯粹，减少条件分叉。

URL 协议层的坑位清单

这一段建议你放进长文，读者会很有共鸣：

  1. file: URL 路径转义问题（空格、大小写、相对路径）。
  2. installbundle: 选项缺失导致无法解析 Bundles。
  3. 额外选项键名不一致，解析成功但语义失效。
  4. 插件名称和描述文件名称不一致，后续依赖解析异常。

上面任何一个都会表现成“看起来像加载器坏了”，实际上是输入不规范。

调试清单（建议直接贴到项目 Wiki）

  1. 启动前：记录当前平台、运行模式、构建配置。
  2. 启动中：抓 ListGameFeaturePlugins 快照。
  3. 启动后：记录每个候选插件是否进入状态机。
  4. 失败时：保存 URL、Policy 判定结果、Descriptor 解析日志。

这份清单越早固化，团队后期越省时间。

进阶练习：做一次“策略灰度发布”

练习目标：不改业务 Action，仅靠 Policy 完成灰度。

  1. 选择一个低风险 Feature，先在本地与测试服放行。
  2. 对正式服保持过滤，验证行为隔离。
  3. 再逐步放量，期间只改 Policy，不改 Action。
  4. 观察日志与状态机轨迹，确认灰度路径可回滚。

这个练习做完后，你就会真正理解“入口治理”为什么比“执行层修补”重要。
