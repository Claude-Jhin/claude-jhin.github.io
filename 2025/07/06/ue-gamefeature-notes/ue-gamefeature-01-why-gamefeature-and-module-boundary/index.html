为什么先讲“边界”

很多团队第一次接触 GameFeature，会把它理解成“可热更新插件”或“高级插件开关”。
这两个说法都不算错，但都不够工程化。

GameFeature 的核心价值，是把“功能上线/下线”做成一个可观察、可回滚、可编排的运行时流程。
它不是单个 API，而是一组协作对象：

  1. UGameFeaturesSubsystem：总调度器
  2. UGameFeatureData：功能清单与资产入口
  3. UGameFeatureAction：激活/停用时真正执行的动作
  4. UGameFeaturePluginStateMachine：状态流转与失败收敛

与传统模块/子系统的分工差异

机制 擅长问题 典型限制
Module 启动时静态装配、编译期组织 运行时按玩法粒度启停成本高
Subsystem 生命周期稳定的全局服务 不擅长“按功能包动态装配资源与行为”
GameFeature 功能包的运行时启停、依赖编排、失败回滚 需要更严格的资源与状态治理

一句话：Subsystem 更像常驻基础设施，GameFeature 更像可编排的功能交付单元。

Lyra 最小复现（实验 1）

目标：先验证“激活即注入，停用即回收”的行为闭环。

  1. 在项目里新建一个 GameFeature 插件（例如 GF_WeaponDebug）。
  2. 创建 GameFeatureData，加入 Add Components Action。
  3. 将目标 Actor 类指向你的 Lyra 角色类（或其派生类），注入一个只做日志的调试组件。
  4. 通过 GameFeature 状态切换到 Active，观察角色是否在运行时拿到新组件。
  5. 切回 Loaded/Registered，确认组件请求被移除。

你要验证的不是“组件是否存在”，而是“状态变化是否严格驱动行为变化”。

常见坑与检查项

  1. 把 GameFeature 当成“仅编辑器配置”，忽略运行时状态机语义。
  2. 只测激活，不测停用，导致线上回收路径失效。
  3. 功能边界过粗，一个 GameFeature 承载过多不相关行为，后续无法独立回滚。

原理下钻：四类对象如何分层协作

在工程上，你可以把 GameFeature 栈分成四层：

  1. 调度层：UGameFeaturesSubsystem，接收目标状态请求并驱动状态机。
  2. 状态层：UGameFeaturePluginStateMachine，处理转移、取消、依赖、失败收敛。
  3. 声明层：UGameFeatureData，声明该功能包包含哪些 Action 和资产扫描规则。
  4. 执行层：UGameFeatureAction，真正把行为注入到世界对象上。

这四层的边界一旦混乱，就会出现两类典型技术债：

  1. 逻辑散落在 Action 里，状态机层无法统一回滚。
  2. 调度层塞业务条件，导致后续无法复用到其他玩法包。

源码主线（长文阅读顺序）

建议按下面顺序读，避免“先钻细节后丢全局”：

  1. 读 GameFeaturesSubsystem.h/.cpp，先看入口能力面。
  2. 读 GameFeatureTypes.h，统一状态名语义。
  3. 读 GameFeaturePluginStateMachine.h/.cpp，理解状态迁移机制。
  4. 回到 GameFeatureData.h/.cpp 与 GameFeatureAction.h/.cpp，落到执行层。

本篇结论

在 UE5.5 里，GameFeature 不是“插件换皮”，而是“功能编排系统”。
后续 2~4 篇我们会把它拆成三条硬链路：入口发现、状态机、Action 执行。

项目实录：我们什么时候决定把功能拆到 GameFeature

这个决策通常不是在架构评审会上做出来的，而是在一次次线上故障里被“逼出来”的。
下面这组现象，在多人项目里非常典型：

  1. 节日玩法下线后，主线玩法还残留事件 Buff。
  2. 一个活动 UI 关闭了，但输入映射没撤，热键冲突。
  3. 临时回滚活动包时，不知道该改哪个模块、删哪段注册代码。

当这些问题反复出现，说明你缺的是“可编排的功能边界”，不是“再多一个 if”。
GameFeature 的价值就在这里：把功能上线、停用、回滚做成显式状态，而不是散落在各个子系统里靠约定执行。

一套可落地的功能拆分法

如果你准备把现有大模块拆成 GameFeature，我建议先按“功能和生命周期”而不是按“代码目录”拆：

  1. 把“必须常驻”的能力留在基础模块（例如账号、匹配、核心战斗循环）。
  2. 把“可启停”的玩法做成独立 Feature（例如限时模式、活动机制、联动内容）。
  3. 把“只影响表现”的内容（UI、音效、局部输入）单独作为可降级层。

拆分时做两个硬约束：

  1. 每个 Feature 必须能独立停用并收敛，不影响主循环。
  2. 任何跨 Feature 依赖都要显式记录，不允许“隐式全局单例”。

旗舰文阅读任务（建议按顺序做）

把这篇当成后续 7 篇的导读，不只是概念介绍。你可以照这个任务单走：

  1. 在引擎源码里建立 GameFeatures 书签组：Subsystem、StateMachine、Data、Action。
  2. 在你自己的项目里选一个“历史上最容易回滚失败”的玩法，尝试映射到 GameFeature 分层。
  3. 画一张你团队自己的“功能边界图”：
    常驻系统 / 可启停系统 / 纯表现扩展。
  4. 用这张图反推过去三个月线上问题，看问题集中在哪一层。

如果第四步做完，通常你会发现：
真正的故障热点大多在“可启停功能却没有状态机约束”的灰色区域。

断点剧本（入门但很实用）

这套剧本适合你第一次跟进 Feature 激活链路：

  1. 断在 OnGameFeatureRegistering，确认插件是否真的进入注册阶段。
  2. 断在 OnGameFeatureLoading，确认 Data 是否可读。
  3. 断在 OnGameFeatureActivating，确认 Action 是否开始执行。
  4. 断在 OnGameFeatureDeactivating，确认回收链路是否完整走完。

每一步都记录三件事：

  1. 插件 URL
  2. 当前状态与目标状态
  3. 当前世界上下文

坚持记录两周后，你的排障速度会明显提高，因为你不再靠“猜是哪层坏了”。

附录：这篇的交付标准（给团队内部对齐用）

如果你要把这篇真的转成团队执行标准，建议要求读者交三样东西：

  1. 一张你项目的 GameFeature 边界图（模块、子系统、Feature 的责任线）。
  2. 一份“可启停功能清单”（哪些内容允许热启停，哪些绝不能动）。
  3. 一条完整激活链路录屏（从请求到 Action 生效再到停用收敛）。

验收时不要只看“能不能跑通”，而要看“能不能解释清楚”：

  1. 为什么这个功能该放在 Feature 而不是常驻模块。
  2. 失败后会回到哪个稳定状态。
  3. 回滚时会影响哪些玩家对象和世界对象。

当团队成员都能把这三点说清楚，后面的章节学习速度会非常快。
