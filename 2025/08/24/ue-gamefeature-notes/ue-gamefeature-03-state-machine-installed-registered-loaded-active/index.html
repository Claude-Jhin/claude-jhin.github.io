先统一语义

很多人把 Active 理解成“已启用”，这太粗了。
在源码里，关键不是“当前状态名字”，而是“当前状态 + 目标区间 + 是否正在转移”。

特别是并发请求下，你会同时遇到：

  1. 旧请求还在跑
  2. 新请求想改目标
  3. 依赖插件也在转移

这就是状态机存在的根本原因。

Installed / Registered / Loaded / Active 的工程含义

  1. Installed：资源安装和挂载基础完成，可被后续识别。
  2. Registered：插件已注册，元数据与描述可用。
  3. Loaded：核心数据（包括 GameFeatureData）已可读，可进入动作准备。
  4. Active：Action 已执行到位，功能对世界可见。

注意：从 Active -> Loaded 不是简单“关开关”，而是完整停用流程。

失败回滚与幂等

这套状态机的价值，在于你不用手写“失败后回到哪个状态”的分支地狱。
只要目标区间设置正确，状态机会在失败、取消、依赖异常时走统一收敛路径。

你需要重点关注两件事：

  1. 同一个插件在短时间内反复改目标时，TryCancel 是否能正确串联。
  2. 依赖插件进入 Terminal 或 Error 分支时，主插件怎么终止而不是半激活。

Lyra 最小复现（实验 3）

目标：观察重入请求下的状态收敛。

  1. 准备一个带 AddComponents 的功能包，初始状态保持 Registered。
  2. 在短时间内连续触发 Registered -> Active -> Loaded -> Active。
  3. 打开 LogGameFeatures，记录每次目标区间变更日志。
  4. 观察最终状态是否稳定在最后一次请求目标，且无残留行为。

这是多人玩法版本迭代时非常常见的真实场景。

常见坑与检查项

  1. 直接假设“调用激活 API 就立即 Active”，忽略异步状态转移。
  2. 只看目标状态，不看当前状态和是否正在 IsRunning()。
  3. 依赖插件异常时没有观测日志，导致主插件失败原因被误判成“自己的 Action 有 bug”。

原理下钻：状态机不是“单目标”，而是“目标区间”

源码里目标不是一个枚举值，而是 FGameFeaturePluginStateRange。
这个设计让状态机可以表达“至少到 Loaded、最多到 Active”这样的区间意图，避免过度耦合到单点状态。

重入与取消：为什么 TryCancel 是必要的

多人项目常见场景：新请求到来时旧请求还在下载、挂载或激活依赖。
TryCancel 的价值是把“抢占”变成显式语义，而不是让两个请求并发踩状态。

依赖联动的真实风险

当父 Feature 激活时，依赖可能处于：

  1. 尚未创建状态机
  2. 正在转移
  3. 已失败并停留在错误状态

状态机通过依赖设置与回调汇总处理这三类情况。
如果你在项目层绕开这套机制直接“手动激活依赖”，后续回滚会变得不可预测。

调试手册（长文版）

  1. 打开 LogGameFeatures，先看每次目标区间变更。
  2. 断在 SetDestination -> UpdateStateMachine，记录当前状态、目标区间、是否运行中。
  3. 出错后不要立刻改 Action，先定位是否是依赖状态机错误或取消重入引发。
  4. 最后才检查业务执行层。

进阶练习

在同一个会话里对同一插件连续执行：

  1. Target=Active
  2. 立刻 Target=Loaded
  3. 再立刻 Target=Active

记录三次请求的完成回调顺序和最终状态，确认你对取消重入语义的理解是否正确。

本篇结论

GameFeature 的状态变更是“请求式 + 异步 + 可取消”的流程。
理解这一点后，才有资格写好后面的 Action 执行与多人边界逻辑。

长文重点：把状态机读成“调度器”，不是“枚举切换器”

很多人第一次读 GameFeaturePluginStateMachine，会盯着状态枚举看。
真正有价值的是把它当成一个小型调度器去读：

  1. 接收外部目标（区间）。
  2. 判断当前是否可直接推进，还是先取消旧请求。
  3. 处理依赖插件联动。
  4. 在每一步里产生日志、回调和错误收敛。

这样读，你会更容易解释“为什么看似只是 Active/Loaded 切换，背后却有很多边界条件”。

典型事故：重复点击激活按钮引发的状态震荡

一个非常常见的线上事故是“按钮被连点”：

  1. 第一次请求把目标设到 Active。
  2. 第二次请求很快把目标改到 Loaded。
  3. 第三次请求又改回 Active。

如果团队对取消重入没有明确约束，就会出现：

  1. 旧回调晚到，覆盖新状态。
  2. 依赖插件提前停用，主插件卡在中间态。
  3. Action 执行次数与回收次数不对称。

状态机提供了机制，但项目代码仍要保证“请求幂等”和“回调时序可观测”。

两个你必须盯住的数据

建议在调试面板里长期暴露两项：

  1. CurrentState
  2. DestinationRange

只看 CurrentState 会有错觉：
你以为插件“已经稳定”，但目标区间可能还在变，状态机仍在调度中。

断点剧本（进阶版）

  1. 断在 ChangeGameFeatureTargetState，记录每次外部请求来源。
  2. 断在 SetDestination，确认是否接受请求或走取消路径。
  3. 断在 TryCancel，看旧请求是否真的被回收。
  4. 断在 UpdateStateMachine 循环，观察真实转移顺序。
  5. 断在失败日志分支，记录终止原因与终止状态。

建议每次调试都导出一份“请求时间线”，否则后续复盘难以还原现场。

实战建议：给状态机加业务层保护带

即使引擎状态机本身很强，你在项目层也应该做两层保护：

  1. 去抖：短时间重复请求先合并，再下发状态机。
  2. 限流：对同一插件设置最小状态切换间隔。

这两层通常能显著减少“高频状态切换导致的偶发异常”。

进阶练习（旗舰版）

做一个“高频切换压测”：

  1. 同一插件 60 秒内随机切换目标状态 200 次。
  2. 同时让两个依赖插件参与联动切换。
  3. 收集成功率、失败率、平均收敛时间、回调乱序次数。
  4. 根据结果调整请求去抖与限流策略。

这组数据非常适合放进长文，会比泛泛的“注意事项”更有说服力。
