本文主题：还原状态机每帧更新与过渡评估顺序，定位“来回切状态”问题（源码长文版）

核心问题

状态机线上故障 80% 不是“不会切”，而是“切得不稳定”：
同一角色在两个状态间高频往返，表现为脚步抖、上半身抽动、Notify 重复触发。

要解决这个问题，必须把每帧真实评估顺序搞清楚，而不是只看图上的箭头。

核心源码锚点：

  • FAnimNode_StateMachine::Update_AnyThread：Runtime/Engine/Private/Animation/AnimNode_StateMachine.cpp:379
  • FindValidTransition：:710
  • UpdateTransitionStates：:854
  • Evaluate_AnyThread：:910
  • EvaluateTransitionStandardBlend：:1000
  • EvaluateTransitionCustomBlend：:1077
  • 转换请求队列 QueuedTransitionEvents 清理/消费：:395、:1491
  • MaxTransitionsPerFrame 默认值：Runtime/Engine/Classes/Animation/AnimNode_StateMachine.h:133（默认构造 :228 为 3）
  • MaxTransitionsRequests：同文件 :138（默认 32）

主线图

每帧执行顺序：和图面直觉哪里不一样

1) Update 会“连续尝试多次过渡”，不是一次

Update_AnyThread 中有一个关键循环：在同一帧内，状态机可能跨越多个状态，直到达到 MaxTransitionsPerFrame 上限。
这就是为什么你会看到“我明明只想 A->B，却在同帧瞬间 B->C”。

2) FindValidTransition 支持递归探索路径

FindValidTransition 不只是检查“当前状态直接边”，它会沿潜在路径递归找合法过渡。
好处是更灵活，风险是：如果规则设计不稳定，你的抖动会被放大而不是被抑制。

3) Transition 事件队列有过期与消费语义

QueuedTransitionEvents 每帧会清理过期请求并消费已处理请求。
如果你把业务事件设计成“每帧都重复塞请求”，会造成规则层看起来“总在被打断”。

4) Evaluate 阶段才真正做过渡混合

Evaluate_AnyThread 根据 ActiveTransitionArray 做标准或自定义混合。
因此一个常见误判是：

  • Update 看到状态切了。
  • 视觉却还在旧状态。

这其实是正常的过渡窗行为，而不是“切换失败”。

切换抖动的四类根因（源码视角）

  1. 输入边界抖动：规则阈值在临界点反复翻转。
  2. 过渡窗冲突：新规则在旧过渡尚未收敛前再次触发。
  3. 事件洪泛：重复 Transition Request 让队列持续被刷新。
  4. 多跳过渡：同帧多次跳转使视觉稳定性下降。

反抖策略：不改引擎也能立刻见效

  1. 给关键规则加滞回（enter/exit 阈值分离）。
  2. 给过渡加最小驻留时间（state dwell time）。
  3. 对事件请求做去重与冷却，避免每帧重发。
  4. 审视 MaxTransitionsPerFrame 是否过高，必要时降低。
  5. 用调试日志把“规则值变化”与“状态变化”同帧打印。

最小验证步骤

  1. 构造 Idle <-> Move 双向切换，阈值都设为同一个临界值（故意制造抖动）。
  2. 每帧记录：输入速度、规则真假、当前状态、ActiveTransitionArray 数量。
  3. 打断点观察 FindValidTransition(:710) 是否在同帧命中多次。
  4. 在规则上加入滞回区间后复测，比较每秒状态切换次数。
  5. 将 MaxTransitionsPerFrame 调低做对照，观察是否缓解多跳抖动。
  6. 输出结论：抖动来自“规则设计”还是“过渡混合参数”。

预期结果：你能把“看起来像动画问题”的抖动，精确还原为可量化的状态机时序问题。

小结

状态机真正的复杂度不在节点数量，而在“同帧多次决策 + 过渡混合 + 事件队列”的组合。
当你沿 Update_AnyThread -> FindValidTransition -> Evaluate_AnyThread 这条链看问题，切换抖动会从玄学变成可验证的系统行为。
