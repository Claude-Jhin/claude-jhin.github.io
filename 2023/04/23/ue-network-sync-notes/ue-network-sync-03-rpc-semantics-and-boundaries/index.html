系列定位：UE5 网络同步源码拆解（5.5）
本文主题：把 RPC 从“会用”提升到“可维护、可审计、可上线”

先把一个误会说破

很多团队口头上会说“我们用 RPC 同步状态”。
这句话不准确，甚至有风险。

RPC 的天然定位是：

  • 传达请求
  • 广播事件

而“长期状态一致性”应该交给属性复制体系。
当你把两者混用，短期可能没问题，长线维护会越来越痛苦。

调用链图

关键函数定位

  • UNetDriver::ProcessRemoteFunction：RPC 进入网络层的总入口。
  • UNetDriver::InternalProcessRemoteFunction：连接/通道级路由与发送。
  • FUNC_NetReliable / FUNC_NetMulticast 分支：可靠性与多播语义。
  • _Implementation：业务逻辑真正执行位置。
  • 权威侧校验逻辑：防滥用、防作弊、防错误输入的最终防线。

RPC 语义先定型：不然后面全乱

我建议团队把 RPC 固定分三类，不要混：

  1. 请求类（Client -> Server）
    • 客户端告诉服务器“我想做什么”
    • 服务器决定“是否允许、是否生效”
  2. 回执类（Server -> Client）
    • 仅对目标客户端下发确认/修正/私有反馈
  3. 广播类（Server -> Multicast）
    • 只发“有展示价值但不承担最终状态”的事件

你会发现，当分类固定后，很多争议会自然消失：

  • 为什么这个逻辑不能写在客户端？
  • 为什么这个事件不能 Reliable Multicast？
  • 为什么这个结果要回到属性复制？

Reliable 与 Unreliable：别靠直觉选

什么场景该 Reliable

  • 一次性关键事件
  • 丢一次会明显破坏状态一致性
  • 频率不高

什么场景优先 Unreliable

  • 高频连续输入
  • 下一帧会覆盖上一帧
  • 更在意实时性，不在意每一帧都送达

两个容易犯错的点

  1. 把高频事件全改 Reliable，结果导致队列压力上升。
  2. 把关键状态变化做成 Unreliable，线上偶发“没收到”又难复现。

安全边界：RPC 到了，不等于可信

这是我最想强调的一段。
很多工程事故不是“RPC 没到”，而是“RPC 到了但没校验”。

服务器 _Implementation 至少要做：

  1. 调用者身份校验（Owner、阵营、权限）
  2. 空间校验（距离、视线、朝向）
  3. 时序校验（冷却、状态机、重复请求窗口）
  4. 频率限制（防滥用/防刷包）

尤其是战斗、交易、交互这类路径，校验缺失会直接变安全问题。

我会怎么跟源码（RPC 诊断顺序）

如果你碰到“RPC 看起来没生效”，不要先改参数，先确认链路：

  1. 业务侧调用点是否真的触发。
  2. ProcessRemoteFunction 是否收到这次调用。
  3. InternalProcessRemoteFunction 是否找到目标连接与通道。
  4. 远端 _Implementation 是否执行。
  5. 执行后是否有权威状态写入和后续复制。

这五步任何一步断了，都会表现成“像成功但不生效”。

可复现问题案例

复现步骤

  1. 客户端在一个无 Ownership 的世界对象上直接调用 Server RPC。
  2. 本地播放交互动画，并打印“发送成功”。
  3. 观察服务器行为与其他客户端状态。

现象

发起者本地看起来交互成功，服务器无权威状态变化，其他客户端无感知。

根因定位

请求路径没有合法 Ownership 支撑，调用没有稳定进入权威执行分支。

最小修复策略

请求统一从拥有对象发起（PlayerController/Character），服务器再路由到目标世界对象执行权威逻辑。
