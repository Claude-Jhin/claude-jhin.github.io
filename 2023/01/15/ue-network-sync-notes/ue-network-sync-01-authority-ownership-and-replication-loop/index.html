为什么先写这篇

我自己带多人玩法项目时，几乎每次网络问题复盘，最后都会回到三个词：

  • Authority（谁拍板）
  • Ownership（谁有资格发请求）
  • Replication Loop（状态到底何时被发出去）

很多 bug 看起来是“参数不对”或“RPC 没触发”，本质其实是这三件事没有统一语义。
所以专栏第一篇不聊技巧，先把语义打平。

一个真实到不能再真实的线上事故

场景很简单：

  1. 客户端按交互键，门打开。
  2. 本地玩家看到门开了，语音里说“我进去了”。
  3. 其他玩家看到门没开，服务器日志也没有“开门成功”。
  4. 3 秒后该玩家被服务器回滚到门外。

当时我们第一反应是“网络抖动”。后来抓链路发现：

  • 门状态由客户端本地改了（不是服务器改）
  • 请求走的是一个没有 Ownership 的对象
  • 该对象本帧甚至没进入有效复制路径

这个事故之后团队统一了一条规矩：

客户端只提交意图；状态写入只能在服务器；复制链路必须可观测。

后面的章节你会看到，这句话在 UE5.5 源码里是有明确落点的。

调用链图

关键函数定位

  • AActor::HasAuthority：先判断当前逻辑有没有资格拍板。
  • AActor::SetOwner / GetOwner：Ownership 决定哪些 RPC 可以合法上行。
  • UNetDriver::ServerReplicateActors：服务器每帧复制主循环。
  • UActorChannel::ReplicateActor：真正把属性和函数写入网络包。
  • UNetDriver::ProcessRemoteFunction：RPC 进入网络层的统一入口。

把三件事讲清：Authority / Ownership / Connection

1. Authority：谁说了算

Authority 不是“谁先执行”，是“谁最终生效”。
客户端可以先播动画、先改 UI、先做预测，但最终状态必须由服务器确认。

工程上最常见误解是：

  • “我在客户端先改值，反正后面会同步”

这句话在多数情况下都危险：

  • 如果服务器不认可这个改动，最终一定回滚；
  • 如果你把表现和状态耦合，回滚时会连带产生抖动和穿模。

2. Ownership：谁有资格发请求

Ownership 决定的是“请求资格”，不是“最终裁决权”。
一个客户端通常只能稳定地通过自己拥有的对象（例如 PlayerController / Character）上行关键请求。

如果你让“世界静态对象”直接接受客户端 Server RPC，经常会遇到：

  • 本地看起来触发了
  • 服务器没执行
  • 没有明确报错

这类问题非常隐蔽，因为它不像空指针会直接炸。

3. Connection：发给谁、什么时候发

连接不是“有网就行”，而是有状态、有预算、有优先级的发送通道。
同一个服务器帧内，并不是所有 Actor 都会被发给所有客户端。

至少会经过：

  1. Relevancy 过滤
  2. Priority 排序
  3. 频率与休眠约束
  4. 通道可用性检查

所以“服务器改了值但客户端没看到”并不等价于“复制系统坏了”，也可能只是这一帧没有发送资格。

复制主循环拆开看（按一帧）

阶段 A：收集候选

UNetDriver::ServerReplicateActors 会为每个连接筛选候选 Actor 集合。
这个阶段决定“谁有资格进入本帧发送队列”。

阶段 B：复制前钩子

对即将复制的 Actor，调用 CallPreReplication。
你可以在这里做动态开关，控制本帧哪些属性参与复制。

阶段 C：通道序列化

进入 UActorChannel::ReplicateActor 后，才是真正的“写包”阶段。
属性增量、子对象复制、RPC 都会在这里汇总到 Bunch。

阶段 D：客户端应用

客户端收包后，经 RepLayout / ObjectReplicator 应用数据，触发 OnRep。
这里是表现更新入口，不是权威决策入口。

我会怎么跟源码（实操路线）

我推荐一条非常稳定的跟读顺序：

  1. 先在 ServerReplicateActors 看这一帧候选数量。
  2. 看目标 Actor 是否命中 CallPreReplication。
  3. 看 ReplicateActor 是否真的写出数据。
  4. 对照 ProcessRemoteFunction，确认 RPC 路径有无被路由到正确连接。
  5. 客户端命中 OnRep 后，再观察表现层是否被二次逻辑覆盖。

只要按这个顺序走，大多数“感觉像网络玄学”的问题都会落地到具体函数。

两个高频误区

误区 1：把 OnRep 当业务逻辑入口

OnRep 适合做表现同步，不适合做权威写入。
如果你在 OnRep 里反向写权威变量，迟早会出现状态打架。

误区 2：把 Server RPC 当状态同步手段

RPC 适合表达“请求”和“事件”，属性复制才是“状态一致性主通道”。
拿 RPC 去堆持续状态，后面排障成本会陡增。

可复现问题案例

复现步骤

  1. 在客户端本地直接修改一个 Replicated 变量（不经 Server RPC）。
  2. 服务器同一变量按固定频率更新。
  3. 观察客户端值和服务器值的轨迹。

现象

客户端会短暂显示本地值，然后被服务器值覆盖，出现“闪变 + 回滚”。

根因定位

客户端本地改动不具备权威性，只会造成短暂视觉偏移，不会成为最终状态。

最小修复策略

客户端只发意图，服务器改状态，再通过属性复制回写客户端。
把“预测表现”和“权威状态”明确拆开。
