本文主题：把“会修 bug”升级成“能持续避免同类 bug”

这篇是全专栏的收束

前 7 篇讲的是机制和策略。
最后这一篇只做一件事：把这些知识变成长期可执行的工程闭环。

我们要避免的不是某一个 bug，而是“同类 bug 反复发生”。

调用链图

关键函数定位

  • PktLag / PktLoss / PktJitter：构造延迟、丢包、抖动环境。
  • p.NetShowCorrections：可视化纠偏频率与幅度。
  • NetTrace 入口：抓网络包时间线与对象热点。
  • stat net：快速观察实时负载。
  • 关键业务日志：请求、权威落地、客户端应用三点闭环。

第一步：先固定复现条件

没有固定复现，后面全部是玄学。
建议团队常驻三档网络配置（写进测试文档）：

  1. 基线档：低延迟、无丢包
  2. 常态档：中延迟、小抖动
  3. 压力档：高延迟 + 抖动 + 少量丢包

每次排障记录必须带上“使用哪一档”。

第二步：证据最小集（必须齐）

我建议每次问题单都附三类证据：

  1. 现象证据：录屏/时间戳
  2. 链路证据：请求 -> 判定 -> 应用三点日志
  3. 资源证据：stat net + Trace 截图

缺任意一类，复盘质量都会下降。

第三步：先归因再修复

很多“修复失败”不是改错代码，而是归错层级。
归因至少分三层：

  1. 复制治理层（候选过大、优先级失真、频率配置失衡）
  2. 预测纠偏层（模型不一致、重放缺失、平滑失配）
  3. 业务表现层（预反馈覆盖权威结果、状态渲染时机错位）

先定层，再改代码，成功率会高很多。

第四步：最小改动原则

排障期最容易犯的错是“大改重构”。
建议固定原则：

  1. 一次只改一个假设对应的最小代码面
  2. 改完立刻在同一网络档位复验
  3. 通过后再扩展到其他档位

这样才能知道“到底是哪个改动起了作用”。

第五步：回归基线要数字化

没有数字化基线，团队会很快回到“感觉良好”的状态。
我建议至少维护三组核心指标：

  1. 一致性指标
    • 状态不一致发生率
    • 关键状态收敛时间
  2. 纠偏指标
    • 单位时间纠偏次数
    • 单次纠偏位移/速度幅度
  3. 带宽指标
    • 峰值带宽
    • 峰值持续时间

每次版本必须与上一版基线对比。

我会怎么跟源码（闭环调试路径）

  1. 在 NetDriver 参数解析路径确认模拟参数已生效。
  2. 在请求入口打时间戳日志。
  3. 在服务器权威写入点打时间戳日志。
  4. 在客户端应用点打时间戳日志。
  5. 用 Trace 对齐三点时间线，判断瓶颈在发送、接收还是应用。

可复现问题案例

复现步骤

  1. 设置 PktLag=120、PktJitter=20、PktLoss=2。
  2. 运行“移动 + 战斗 + 交互”混合场景 5 分钟。
  3. 采集 stat net、纠偏可视化和三点日志。

现象

偶发技能状态晚到、局部回弹、个别对象更新饥饿。

根因定位

低价值对象复制突刺挤占预算，同时预测平滑窗口偏短，叠加造成体验波动。

最小修复策略

先治理复制峰值（可见性/优先级/频率/休眠），再调整预测平滑参数；
同档位复验通过后再扩展到其他档位。

排查顺序（实战版）

上线前网络回归清单（建议直接落到 CI）

  1. 三档网络条件必须全跑。
  2. 每档必须覆盖移动/战斗/交互三类核心循环。
  3. 每次改动必须产出三点日志与指标快照。
  4. 指标超过阈值自动告警（不靠人工“看感觉”）。
  5. 关键玩法改动必须附最小复现实验脚本。

写在最后

到这里，这个专栏真正想建立的不是“某一套技巧”，而是“同一套工作方式”。

当团队把网络问题当作可观测、可归因、可回归的工程对象，
多人同步才会从“靠经验救火”变成“持续稳定迭代”。

这就是我理解的源码阅读价值：不是为了记住函数名，而是为了让项目少走弯路。
