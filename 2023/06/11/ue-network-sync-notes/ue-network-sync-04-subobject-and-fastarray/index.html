这篇解决什么

前面两篇讲的是基础机制。
到了真正的项目里，你很快会遇到更麻烦的数据形态：

  • 背包列表
  • Buff 列表
  • 技能槽/冷却队列
  • 可增删改的运行时对象集合

这类数据最大的特点是：

  • 变化频率高
  • 结构会变化（增删重排）
  • 业务回调链长（UI、动画、数值系统）

如果还按“普通属性复制”思路硬上，基本都会在带宽或一致性上吃亏。

调用链图

关键函数定位

  • AActor::AddReplicatedSubObject：注册可复制子对象。
  • AActor::ReplicateSubobjects：子对象复制扩展入口。
  • FFastArraySerializer::MarkItemDirty：元素级脏标记。
  • FFastArraySerializer::MarkArrayDirty：结构级脏标记。
  • FFastArraySerializer::FastArrayDeltaSerialize：增量序列化核心。

先决定“对象边界”再写同步

我建议先做一个建模动作：

  1. 哪些是“对象级状态”（适合子对象）
  2. 哪些是“集合级状态”（适合 FastArray）
  3. 哪些是“可推导表现”（不要复制）

如果这个边界没定清楚，后面会出现两个典型后果：

  • 同步过多：带宽吃紧
  • 同步不足：客户端逻辑拼不出正确状态

子对象复制与 FastArray 的分工

子对象复制（Subobject）

解决“生命周期与职责域”：

  • 某一类逻辑状态属于哪个组件/子系统
  • 该子系统是否独立复制、何时复制

FastArray

解决“集合增量”：

  • 新增/删除/更新的最小粒度
  • 高频变更不走全量
  • 客户端可以按变更类型响应

推荐组合形态：

  • 外层：UInventoryComponent（可复制子对象）
  • 内层：FInventoryList : FFastArraySerializer
  • 元素：FInventoryItem : FFastArraySerializerItem

这两个标记一定要形成团队纪律

MarkItemDirty

改了某个元素字段，就必须标记。
漏标记 = 本帧不发 = 客户端暂时不一致。

MarkArrayDirty

删元素、重排、整体结构变化，就必须标记。
只改容器结构不标记，客户端常会表现成“隔几帧才突然对齐”。

我的实践建议很直接：

  • 禁止业务代码直接改底层容器
  • 统一走封装写接口
  • 接口内部强制完成脏标记

常见误区

误区 1：拿普通 TArray 复制高频列表

能跑，但在人数和频率上来后，几乎一定吃亏。

误区 2：把“字段更新”和“结构更新”混成一个标记

这会让客户端回调语义不清晰，调试日志也会混乱。

误区 3：客户端回调只处理新增，不处理删除

最典型后果：UI 残留、状态泄漏、偶发崩溃。

我会怎么跟源码（复杂状态排障）

  1. 写入口打点：确认每次改动是否触发对应 Mark*Dirty。
  2. FastArrayDeltaSerialize 断点：确认变更是否进入增量包。
  3. ReplicateSubobjects 断点：确认所属对象本帧是否参与复制。
  4. 客户端应用回调：确认增删改分支是否齐全。
  5. UI 刷新链：确认有没有旧缓存覆盖新状态。

可复现问题案例

复现步骤

  1. Buff 列表使用 FastArray。
  2. 服务器修改某条 Buff 层数，但没有调用 MarkItemDirty。
  3. 在客户端观察 Buff 面板与战斗结算。

现象

服务器状态已更新，客户端某些时刻不更新，直到后续结构变化才突然跳变。

根因定位

增量发送依赖脏标记；漏标记就不会进入本帧复制数据。

最小修复策略

将所有列表写操作收敛到统一 API，API 内部强制标记脏数据并记录日志。

排查顺序（实战版）

数据建模清单（这篇要沉淀的东西）

  1. 状态字段和表现字段分离。
  2. 高频集合优先 FastArray。
  3. 写路径唯一化，脏标记强约束。
  4. 客户端回调语义固定为新增/更新/删除三类。
  5. 每次结构改动必须配一条回归用例。

小结

复杂状态同步最怕“先写功能，后补规则”。
规则应该先于功能：边界先定，写入收口，增量明确，回调可审计。
