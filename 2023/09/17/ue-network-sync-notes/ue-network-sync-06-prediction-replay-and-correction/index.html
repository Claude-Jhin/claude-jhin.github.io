系列定位：UE5 网络同步源码拆解（5.5）
本文主题：把“回弹、抖动、纠偏风暴”还原成可验证的协议问题

先讲一个常见误判

项目里经常听到一句话：

“这个角色抖，是平滑参数没调好。”

有时对，但不是多数情况。
更多时候，平滑只是把底层错误暂时抹平，真正根因是：

  • 客户端预测模型和服务器模型不一致
  • 输入快照协议不完整
  • 纠偏后没有正确重放

这篇我们就把它拆成协议问题来谈，而不是“手感玄学”。

调用链图

关键函数定位

  • ReplicateMoveToServer：客户端预测上行入口（CMC 典型实现）。
  • FSavedMove_Character：输入快照、重放、合并策略。
  • ServerMove_HandleMoveData / PerformMovement：服务器重演与权威执行。
  • ClientAdjustPosition_Implementation：纠偏接收与应用。
  • SmoothClientPosition：视觉层平滑。

把 CMC 抽象成通用预测协议

虽然这些函数在移动组件里，但协议思想可以迁移到任何高频交互：

  1. 输入要可编号
  2. 状态要可重演
  3. 差异要可度量
  4. 纠偏要可回放
  5. 表现要可平滑

如果你自己写冲刺、滑铲、攀爬、载具、近战位移，都能直接复用这套骨架。

为什么“模型一致性”一定排第一

模型一致性一旦破坏，后面所有优化都会变成补丁。

常见破坏来源：

  1. 客户端多了一段本地加速逻辑。
  2. 服务器用了不同参数表或曲线版本。
  3. 快照里漏传了影响结果的关键状态。
  4. 不同平台浮点路径差异未收敛（极端场景下会放大）。

判断方式很简单：

  • 在相同输入序列下，双端重演轨迹是否一致。

不一致就先修模型，不要先调平滑。

纠偏不是坏事，纠偏风暴才是坏事

健康系统里，纠偏应该是“偶发、可控、可解释”。
危险信号是：

  • 高频连续纠偏
  • 同一交互动作每次都纠偏
  • 纠偏后下一帧继续纠偏

这通常意味着协议闭环不完整。

我会怎么跟源码（预测排障顺序）

  1. 客户端快照记录（确认输入序号和关键状态都在）。
  2. 服务器重演入口（确认按同序列执行）。
  3. 权威结果比较（确认误差阈值策略）。
  4. 客户端纠偏应用（确认 ACK 与重放流程）。
  5. 平滑层（只管视觉，不改权威状态）。

调试开关：别浪费

p.NetShowCorrections 是非常好用的入口。
配合日志，你至少要回答三件事：

  1. 每分钟纠偏次数
  2. 单次纠偏幅度
  3. 纠偏后稳定时长

没有这三项数据，调平滑参数大概率靠感觉。

可复现问题案例

复现步骤

  1. 自定义冲刺支持客户端预测。
  2. 冲刺加速度只在客户端读取新配置，服务器仍是旧配置。
  3. 在 120ms RTT + 抖动场景做连续转向冲刺。

现象

角色出现“前冲一小段再被拉回”，纠偏频率显著上升。

根因定位

预测模型与权威模型分叉，误差持续累积，触发纠偏风暴。

最小修复策略

统一参数来源，必要时把关键配置纳入快照校验；确保纠偏后重放链路完整。

排查顺序（实战版）

预测纠偏清单（建议落文档）

  1. 输入必须可编号、可追踪。
  2. 关键状态必须进快照。
  3. 服务器必须可重演同序列。
  4. 纠偏必须绑定重放机制。
  5. 平滑层不参与权威判定。
  6. 每次改动必须跑网络模拟回归。

小结

预测系统的核心不是“看起来丝滑”，而是“在延迟和抖动下仍然可解释”。
可解释，才可维护；可维护，才可上线。
