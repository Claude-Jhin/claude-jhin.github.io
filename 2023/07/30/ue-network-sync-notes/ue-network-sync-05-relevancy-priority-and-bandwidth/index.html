系列定位：UE5 网络同步源码拆解（5.5）
本文主题：把网络带宽当作有限资源来调度，而不是无限广播通道

为什么这篇通常决定项目上限

在小规模测试里，很多同步策略都“看起来能用”。
一旦人数、对象密度、战斗频率上来，带宽治理就是第一道硬门槛。

常见线上症状：

  • 关键对象更新偶发延后
  • 非关键对象却持续占预算
  • 网络图表里峰值突刺频繁

这些问题很少靠“单个参数”解决，必须回到治理顺序本身。

调用链图

关键函数定位

  • AActor::IsNetRelevantFor：连接维度可见性过滤。
  • AActor::GetNetPriority：预算不足时的发送优先级。
  • SetNetUpdateFrequency / SetMinNetUpdateFrequency：发送频率控制。
  • SetNetDormancy / FlushNetDormancy：静态对象休眠与唤醒。
  • UReplicationGraph::ServerReplicateActors：大规模分桶调度入口。

治理顺序必须固定（过滤 > 排序 > 频率 > 休眠）

这是我在项目里踩过最多坑的一段。

第一步：先过滤

如果候选集合本身就过大，后面怎么调频率都只是“缓解”，不是“解决”。

第二步：再排序

预算不足是常态，不是异常。
所以你必须明确“谁先发”，而不是默认大家公平排队。

第三步：最后才调频率

频率调优是细化动作，不是第一性动作。
先过滤和排序，频率调参才有意义。

第四步：静态对象休眠

长期不变对象应该尽早休眠，不要每帧都参与昂贵评估。

Replication Graph 的真实价值

很多人把 Replication Graph 当“优化插件”。
更准确的说法是：它是“复制候选构建方式”的升级。

不使用 RepGraph 时，调度更接近单表遍历思路；
使用 RepGraph 后，能更自然地按：

  • 空间
  • 类别
  • 连接特定上下文

做分桶聚合，减少无效扫描。

所以它解决的不是一个参数，而是复杂度结构。

NetUpdateFrequency 不是越高越好

高频更新并不等于高质量同步。
如果对象价值低、可见性弱、变化稀疏，高频只会浪费预算。

我的经验是先做对象分层，再给分层设置频率区间：

  1. 战斗关键对象：高优先 + 稳定频率
  2. 次级表现对象：中频
  3. 装饰对象：低频或休眠

我会怎么跟源码（带宽问题排障）

  1. 在 ServerReplicateActors 看每连接候选规模。
  2. 跟 IsNetRelevantFor 看过滤是否过宽。
  3. 跟 GetNetPriority 看排序是否符合业务价值。
  4. 检查运行时是否有代码覆盖 NetUpdateFrequency。
  5. 对静态对象核查 Dormancy 是否真正生效。
  6. 若已启用 RepGraph，跟 GatherActorListsForConnection 看节点输出结构。

可复现问题案例

复现步骤

  1. 场景内放置大量低价值可复制对象，并给较高更新频率。
  2. 多人同屏高强度战斗。
  3. 采集 stat net 和关键对象延迟表现。

现象

关键战斗状态偶发晚到，低价值对象却持续占用发送预算。

根因定位

候选集合过大 + 排序规则未体现业务价值，导致关键对象预算被挤压。

最小修复策略

先做对象分层，收紧低价值对象 Relevancy 与频率，再提升关键对象优先级。

排查顺序（实战版）

工程建议：把治理写成配置约定

建议在项目里固定一份“复制治理表”，至少包含：

  1. 对象分类
  2. Relevancy 策略
  3. Priority 规则
  4. 频率区间
  5. Dormancy 策略

这样新功能接入时，不会每次都从零拍脑袋。

小结

复制治理本质是资源调度。
你给谁预算、在哪个时机给、为什么给，决定了多人体验的上限。
