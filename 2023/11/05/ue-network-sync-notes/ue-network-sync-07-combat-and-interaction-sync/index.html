本文主题：把“战斗里最难吵清楚的问题”拆成一套可执行的工程规则

这一篇想回答什么

多人战斗同步里最容易陷入争论的三个词是：

  • 手感
  • 公平
  • 成本

它们经常彼此冲突。
这篇不追求银弹，而是给一套“可落地、可复盘、可扩展”的权衡框架。

调用链图

关键函数定位

  • LineTraceSingleByChannel / Sweep：服务器权威命中判定基础。
  • UGameplayStatics::ApplyPointDamage / ApplyDamage：伤害链路入口。
  • AActor::TakeDamage：最终伤害处理落点。
  • bReplicateMovement / OnRep_ReplicatedMovement：投射物与运动对象的复制基础。
  • Server RPC + 属性复制：请求与结果职责分离主线。

战斗同步先定“判定层级”

建议固定三层：

  1. 客户端预反馈层
    • 只负责即时体感（枪口火花、挥刀轨迹、本地手柄反馈）
  2. 服务器权威判定层
    • 负责命中成立与否、伤害结算、状态写入
  3. 结果同步层
    • 把权威结果传播给所有相关客户端

当三层明确后，很多争议会自动消失：

  • 为什么本地命中不等于真实命中
  • 为什么客户端看到“打中”但没扣血
  • 为什么有些表现必须延后到权威确认后再播

命中与伤害链路怎么拆

命中判定

服务器用 Trace/Sweep 做权威判定。
客户端可以做预测，但不能作为最终依据。

伤害结算

通过 ApplyPointDamage/ApplyDamage 进入 TakeDamage。
真正改变血量、护盾、状态机必须在权威侧完成。

结果传播

  • 持续状态：属性复制
  • 一次性表现：事件广播（谨慎使用 Multicast）

投射物同步：别只看位置

只开 bReplicateMovement 只能解决“飞到哪”。
战斗系统还要额外保证：

  1. 谁生成（生成权）
  2. 谁判定命中（判定权）
  3. 谁写结果（结果权）

如果三权不收口，投射物会变成争议制造机。

延迟补偿不是开关，是策略集合

同一个“延迟补偿”在不同武器/技能上策略应该不同：

  1. 命中窗口长度
  2. 可补偿的目标类型
  3. 可补偿的历史范围
  4. 对公平性的容忍边界

建议按武器或技能类别配置，而不是全局一刀切。

我会怎么跟源码（战斗同步排障）

  1. 请求上行点：确认客户端上传的是意图，不是结果。
  2. 服务器判定点：确认判定输入完整（位置、时间、状态）。
  3. 伤害落地点：确认 TakeDamage 执行且写入权威状态。
  4. 结果复制点：确认状态是否正确传播到相关客户端。
  5. 表现触发点：确认预反馈与权威反馈不会互相覆盖。

可复现问题案例

复现步骤

  1. 客户端本地先判定命中并立即扣本地血量显示。
  2. 服务器判定该次命中无效。
  3. 在 120ms RTT 场景连续触发。

现象

玩家看到“先掉血后回弹”，体感为不公平，复盘难度高。

根因定位

预反馈和权威结果没有分层；本地状态与权威状态混写。

最小修复策略

客户端仅做轻量预反馈；真实血量与状态只接受服务器写入并通过复制回写。

排查顺序（实战版）

工程落地建议

  1. 每个战斗行为都标注“请求层/权威层/表现层”责任归属。
  2. 关键技能必须有高延迟回归脚本。
  3. 命中争议必须可还原到日志三点：请求、判定、应用。
  4. 对玩家可见的“回弹”建立量化阈值（频率、幅度、持续时长）。

小结

战斗同步不是“让客户端看起来永远正确”，而是“在延迟环境里让权威结果稳定且可接受”。
你要管理的不是一次命中，而是长期体验曲线。
