系列定位：UE5 网络同步源码拆解（5.5）
本文主题：把“声明一个 Replicated 变量之后到底发生了什么”完整走一遍

先说结论

多人项目里，属性复制问题最容易被低估。
因为它看起来像“加一个宏就行”，实际上它是四层机制叠起来的结果：

  1. 声明层：你想同步什么
  2. 规则层：这一帧允许发给谁
  3. 序列化层：本帧到底写了哪些差异
  4. 应用层：客户端怎么落地、怎么触发回调

只要有一层没想明白，就会出现经典症状：

  • 服务器值明明改了，客户端不变
  • 客户端偶发变，下一帧又回去
  • OnRep 时有时无，看起来像随机

调用链图

关键函数定位

  • AActor::GetLifetimeReplicatedProps：声明复制属性与条件。
  • DOREPLIFETIME_* 宏：定义复制策略（条件、通知）。
  • AActor::PreReplication：复制前动态筛选。
  • FObjectReplicator::ReplicateProperties：本帧属性打包入口。
  • FRepLayout::ReplicateProperties：差异序列化核心。
  • FRepLayout::ReceiveProperties：客户端接收应用。

一条完整路径：从定义到客户端生效

第 1 步：声明复制意图

你在类里写 UPROPERTY(Replicated) 或 ReplicatedUsing，本质是在声明“这不是本地字段，而是网络状态的一部分”。

然后在 GetLifetimeReplicatedProps 注册到生命周期列表里。
这一步漏了，后面都不会发生。

第 2 步：复制前筛选

PreReplication 是非常关键但经常被忽略的点。
很多团队会在这里做“临时过滤”，比如：

  • 某类状态只在战斗中同步
  • 某些冗余字段在静止时跳过

这没问题，但前提是你自己要有“可观测性”。
否则几周后你自己都忘了这里有个动态开关。

第 3 步：差异序列化

FObjectReplicator + FRepLayout 会比较状态差异并写包。
注意关键词是“差异”：

  • 没变化，不发
  • 条件不满足，不发
  • 本帧没进复制通道，也不发

这解释了一个高频误解：

“我每帧都写这个值，为什么客户端有时候不触发 OnRep？”

如果写的是同值，系统可能不会形成可发送差异。

第 4 步：客户端应用与通知

客户端 ReceiveProperties 成功后，才进入 OnRep。
OnRep 的职责是“收到之后怎么展示”，而不是“决定是否应该同步”。

REPNOTIFY 该怎么选：OnChanged 还是 Always

UnrealNetwork.h 里有很明确的语义：

  • REPNOTIFY_OnChanged：默认选项，值变了再回调
  • REPNOTIFY_Always：每次收到都回调

我的经验是：

  1. 默认先 OnChanged
  2. 只有明确需要“重复通知语义”的地方才 Always
  3. 一旦用 Always，OnRep 里必须避免重逻辑

常见反例：

  • 在 OnRep 里全量重建 UI
  • 在 OnRep 里再次写网络状态
  • 在 OnRep 里触发不幂等副作用

我会怎么跟源码（实际排障步骤）

如果你遇到“属性不同步”，我建议按下面顺序排：

  1. 看 GetLifetimeReplicatedProps：变量是否真的注册。
  2. 看 PreReplication：有没有被你动态过滤掉。
  3. 看 FObjectReplicator::ReplicateProperties：本帧有没有写出差异。
  4. 看 FRepLayout::ReceiveProperties：客户端有没有正确应用。
  5. 看 OnRep：表现是否被别的逻辑覆盖。

这个顺序的价值在于：每一步都能回答“到底是没发、没到、还是到了但被覆盖”。

两个项目里最常踩的坑

坑 1：把状态同步和事件广播混成一件事

例如血量变化：

  • “当前血量是多少”是状态
  • “播放一次受击闪红”是事件

如果你试图用一个变量同时表达两者，迟早出问题。

坑 2：把 OnRep 当业务主入口

OnRep 的触发时机取决于复制系统，不应该承载“必须执行”的权威业务。
业务关键逻辑要在服务器状态写入侧收口。

可复现问题案例

复现步骤

  1. Health 使用 RepNotify。
  2. 服务器在短时间内多次写入同一个值（例如都写 80）。
  3. 客户端 UI 绑定在 OnRep_Health。

现象

客户端偶发不刷新，团队误判为“OnRep 不稳定”。

根因定位

复制系统按差异发送；重复写同值不会形成新差异，也就不会触发新的通知语义。

最小修复策略

把“状态变化”与“表现事件”拆开：

  • 状态走属性复制
  • 需要每次触发的表现走独立事件通道（RPC 或事件字段）
