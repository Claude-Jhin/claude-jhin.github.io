核心问题

动画线上问题最常见的误判是：把所有问题都归到 AnimGraph 逻辑。
在 UE5.5 里，真正有效的第一刀是把问题先归类到两个阶段：

  1. Update 阶段：状态、时间、权重、Montage 进度如何变化。
  2. Evaluate 阶段：如何把当前帧的节点状态求值成最终 Pose。

只要先判断“错在 Update 还是 Evaluate”，排查空间通常立刻缩小 50% 以上。

这篇先把一帧主线钉死到 USkeletalMeshComponent：

  • TickComponent：Engine/Source/Runtime/Engine/Private/Components/SkeletalMeshComponent.cpp:1843
  • TickAnimation：:1541
  • RefreshBoneTransforms：:2579
  • DispatchParallelEvaluationTasks：:2775
  • PerformAnimationEvaluation：:2301
  • ParallelAnimationEvaluation：:4346
  • CompleteParallelAnimationEvaluation：:4439
  • FinalizeBoneTransform：:4577

并行相关总开关同文件顶部：

  • a.ParallelAnimEvaluation：:62

源码拆解：一帧到底做了什么

1) TickComponent 只负责“调度语义”，不负责具体求值

TickComponent 是动画系统接入 Actor 组件 Tick 的入口。它做的关键事不是“算姿态”，而是决定本帧动画子系统要走哪条分支：

  • 是否允许 Tick（可见性、暂停、注册状态、骨架有效性）。
  • 是否需要 TickAnimation。
  • 是否触发后续 RefreshBoneTransforms。

这里就已经会受到 URO（Update Rate Optimization）和外部 Tick 控制影响。所以很多“偶发一帧不对”的问题，根因并不在节点，而在这里被跳帧/插帧策略改写了时序。

2) TickAnimation 是 Update 主入口：推进状态，不产出最终骨骼

TickAnimation 的核心是驱动 AnimInstance 进入本帧 Update：

  • 采样输入变量（通常仍在 GameThread）。
  • 推进状态机和资产播放器的时间。
  • 推进 Montage 权重、队列与事件。

注意这里“更新的是状态”，不是“输出最终 Pose”。如果你在这里断点看到变量正确，但角色姿态仍错，不矛盾，问题可能在 Evaluate。

3) RefreshBoneTransforms 决定本帧 Evaluate 策略

RefreshBoneTransforms 是总控点。它会综合判断：

  • 本帧是否应该真正做 Evaluate。
  • 是否走并行任务图。
  • 是否需要对跳过帧做插值。

由它进入 DispatchParallelEvaluationTasks 后，再分流到 ParallelAnimationEvaluation（worker 执行）与 CompleteParallelAnimationEvaluation（回收结果）。

4) PerformAnimationEvaluation 真正把图变成姿态

PerformAnimationEvaluation 是“图求值 -> Pose 输出”的关键函数。这里会：

  • 调用 AnimInstance/Proxy 的 Evaluate 路径。
  • 输出 OutSpaceBases、OutBoneSpaceTransforms、OutCurve、OutAttributes。
  • 在启用 Post Process 的情况下，叠加后处理实例的结果。

这意味着：Blend、StateMachine、Slot、LayeredBoneBlend 的绝大部分“数学结果”，都在这一层收敛。

5) FinalizeBoneTransform 负责最终落地与一致性

FinalizeBoneTransform 把前面得到的骨骼结果写回组件最终状态。
很多“看上去像动画图错了”的现象，其实是这个阶段才暴露出来，比如：

  • 骨骼缓存无效导致的重新计算开销尖峰。
  • Root Motion 与角色胶囊位移时序不同步。
  • URO 插值帧上视觉抖动。

常见误判与定位捷径

误判 1：变量对了，姿态就一定对

反例：NativeUpdateAnimation 里速度变量完全正确，但 Evaluate 侧某个 Layer 权重没进来，最终姿态仍错。

误判 2：并行一定更快

反例：角色数量少、图很小、任务分发开销占比高时，a.ParallelAnimEvaluation=0 反而可能更稳。

误判 3：抖动都是状态机问题

反例：状态稳定，但 URO 插值与 Root Motion 回写组合导致视觉抖动。

最小验证步骤

  1. 在本地打开 stat anim、stat taskgraph、ShowDebug Animation，记录默认基线。
  2. 在以下位置打断点并记录单帧调用顺序：
    TickAnimation(:1541) -> RefreshBoneTransforms(:2579) -> PerformAnimationEvaluation(:2301) -> FinalizeBoneTransform(:4577)。
  3. 切换 a.ParallelAnimEvaluation 1/0，对比：
    主线程时间、任务线程时间、视觉结果是否一致。
  4. 打开/关闭 a.ParallelAnimUpdate，观察 Update 阶段线程迁移是否影响自定义逻辑。
  5. 人为构造一个“输入正确但姿态错误”案例，强制你先判断它属于 Update 还是 Evaluate。
  6. 输出一页定位记录：现象、阶段归类、关键函数、下一步实验。

预期结果：你会得到一条稳定的排障起点，而不是每次从 AnimGraph 图面盲猜。

小结

这篇建立的是“统一坐标系”：先看帧主线，再看节点细节。
下一篇会进入 UAnimInstance 与 FAnimInstanceProxy，把生命周期、线程边界和可并行数据契约讲透。
当你能清楚回答“这帧到底在哪条线程、哪个阶段改了什么”，动画系统就从黑盒变成白盒。
