写在前面

这一篇不聊参数，先只看“骨架”。
因为我自己排移动问题时，第一件事永远不是调数值，而是确认主链有没有跑通：
TickComponent -> PerformMovement -> StartNewPhysics。

调用链图

关键函数定位

  • UCharacterMovementComponent::TickComponent：一帧移动更新总入口。
  • UCharacterMovementComponent::PerformMovement：处理根运动、状态前后更新并驱动物理解算。
  • UCharacterMovementComponent::StartNewPhysics：按 MovementMode 分发到 PhysWalking/PhysFalling/PhysCustom。
  • UCharacterMovementComponent::SafeMoveUpdatedComponent：执行实际位移与碰撞响应。
  • UCharacterMovementComponent::SlideAlongSurface：处理撞墙后的切向滑动。

我会怎么跟源码

这段最省时间的方法，就是在同一个文件里顺着调用链往下走：

  1. 打开 Engine/Source/Runtime/Engine/Private/Components/CharacterMovementComponent.cpp。
  2. 搜索 UCharacterMovementComponent::TickComponent(，定位一帧入口。
  3. 在同文件搜索 PerformMovement( 与 StartNewPhysics(，确认主链调用顺序。
  4. 再搜索 PhysWalking(、PhysFalling(、PhysCustom(，验证不同模式的分发落点。
  5. 断点建议：TickComponent -> PerformMovement -> StartNewPhysics 连续断点，先看“链路通不通”，再看具体分支。

可复现问题案例

复现步骤

  1. 自定义 UCharacterMovementComponent 并重写 TickComponent。
  2. 只写自定义逻辑，不调用 Super::TickComponent(...)。
  3. 运行后观察角色输入与位移。

现象

输入事件正常触发，但角色完全不移动或状态机卡死在旧状态。

根因定位

跳过 Super::TickComponent 后，PerformMovement -> StartNewPhysics 主链没有被执行，整帧移动物理更新被短路。

最小修复策略

保留 Super::TickComponent，把自定义逻辑放在调用前后明确的位置；若要替换分支，优先覆写 Phys* 或 OnMovementUpdated 而不是截断总入口。

排查顺序（实战版）

收尾

移动系统调优之前，先确认主骨架是活的。
这条链一旦断了，后面再细的参数都不会真正生效。

深入一层：这一帧到底是怎么跑起来的

如果只记一句话：
TickComponent 不是“直接做物理”，它是一个调度入口，先判断角色身份和网络场景，再决定走哪条执行路径。

在 UE_5.5 的 CharacterMovementComponent.cpp 中可以看到三个常见分流：

  1. 本地可控角色：ControlledCharacterMove
  2. 服务端代管远端客户端：ServerAutonomousProxyTick
  3. 模拟代理：SimulatedTick + 网络平滑

也就是说，你看见“角色不动”，第一反应不该是 PhysWalking，而是先确认你到底进了哪条大分支。

所以“当前 MovementMode 是什么”永远是你断点时第一件要确认的事。

TickComponent 的几个关键前置判断

TickComponent 开头有几道门槛，经常直接决定你后面能不能进物理：

  1. HasValidData()
  2. ShouldSkipUpdate(DeltaTime)
  3. UpdatedComponent->IsSimulatingPhysics()
  4. CharacterOwner->CheckStillInWorld()

你只要命中任意一个早退条件，后面 PerformMovement 就不会跑。
这也是为什么很多“偶现不动”其实是数据有效性问题，不是移动参数问题。

PerformMovement 并不只是“调用 Phys”

很多人把 PerformMovement 理解成“简单转发到 StartNewPhysics”。
实际上它做了不少关键工作，顺序很重要：

  1. 处理 root motion 和外力状态。
  2. ClearJumpInput（清当前跳跃输入，为下一帧事件留空间）。
  3. 调用 StartNewPhysics 进入具体模式。
  4. UpdateCharacterStateAfterMovement。
  5. 处理旋转与 root motion 旋转补偿。

这几步意味着：
你如果在 PhysWalking 里看见“输入状态不对/旋转不对”，根因可能在 PerformMovement 前半段，不一定在 walking 逻辑本身。

StartNewPhysics 的边界条件

StartNewPhysics 还有两个很关键的防护：

  • deltaTime < MIN_TICK_TIME
  • Iterations >= MaxSimulationIterations

这两个判断会在高抖动帧、超大 DeltaTime、复杂碰撞场景下影响结果。
如果你遇到“低帧率下手感和高帧率不一致”，这个入口一定要看。

角色身份（Role）对主链的影响

很多“本地正常、联机异常”的移动 bug，实质是角色身份分支没想清楚。

你可以按下面这个心智模型看：

  1. ROLE_Authority：服务器权威模拟。
  2. ROLE_AutonomousProxy：客户端本地预测 + 上报。
  3. ROLE_SimulatedProxy：主要吃复制与平滑，不跑完整本地控制逻辑。

对应到源码里，ControlledCharacterMove 的分支（...:6240 之后）很直白：

  • Authority -> PerformMovement
  • AutonomousProxy + Client -> ReplicateMoveToServer

这就是为什么你在客户端看起来“动了”，但服务器可能不同意，然后回拉。

诊断顺序：先大分支，后小分支

我建议调试顺序固定成这样：

  1. TickComponent 是否执行。
  2. 角色身份分支是否正确。
  3. PerformMovement 是否进入。
  4. StartNewPhysics 是否进入且 MovementMode 是否符合预期。
  5. 对应 Phys* 分支是否稳定命中。

好处是你不会一上来就陷在某个 PhysWalking 细节里，结果其实主链根本没跑到。

常见“看起来像参数问题，实际是骨架问题”的 case

case 1：改了很多 MaxWalkSpeed 但角色还是不动

通常不是速度参数问题，而是：

  • ShouldSkipUpdate 命中
  • UpdatedComponent 在模拟物理
  • MovementMode 已经被切到 MOVE_None

case 2：联机下偶发“瞬停”

常见是客户端进了 ReplicateMoveToServer，但本地 SavedMove 或后续 correction 逻辑触发，导致你视觉上像“突然断帧”。

case 3：自定义组件覆写后彻底失效

最常见就是覆写 TickComponent 忘了 Super::TickComponent，这会直接掐掉骨架主链。
