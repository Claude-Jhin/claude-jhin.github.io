本文主题：读通技能从“被赋予”到“被结束”的完整执行主线

GA 的职责边界

GameplayAbility（GA）是“可执行动作单元”。
它适合承载技能、交互、被动效果，不适合承载底层移动输入或纯 UI 工作流。

一个实用判断标准：

  1. 需要和 Cost、Cooldown、Tag 条件、预测系统联动的行为，优先放 GA。
  2. 只涉及本地 UI 的行为，尽量别硬塞进 GA。

生命周期：从赋予到激活再到结束

GA 的运行过程可以拆成三段：

  1. GiveAbility：在服务器赋予，生成 GameplayAbilitySpec 并复制给所属客户端。
  2. TryActivateAbility：输入或事件触发，经过条件检查进入激活。
  3. EndAbility / CancelAbility：自然结束或外部终止，回收运行态。

在本地预测 GA 中，客户端会先激活，服务器后校验。
校验失败时会触发回滚，所以激活逻辑必须考虑“被撤销”的路径。

输入绑定：最常见的稳定坑点

输入接入 ASC 时，推荐把输入枚举和项目输入动作建立清晰映射。
如果 ASC 在 PlayerState 上，还要特别注意客户端时序：

  1. SetupPlayerInputComponent 可能先于 PlayerState 可用。
  2. OnRep_PlayerState 可能早于 InputComponent 创建。

工程上常见做法是两边都尝试绑定，并用布尔防重。

Instancing、Net Execution、Net Security

这三组策略决定技能的运行方式：

  1. Instanced Per Actor：最常用，单 ASC 复用实例。
  2. Instanced Per Execution：每次激活新建实例，隔离强但成本高。
  3. Non-Instanced：最轻量，限制也最多，适合非常简单高频能力。

网络执行策略决定谁先跑：

  1. Local Predicted：重体验，客户端先执行。
  2. Server Only：重权威，服务器执行。
  3. Local Only / Server Initiated：按具体玩法场景使用。

网络安全策略则决定客户端是否有权发起执行和终止请求，建议显式配置，不靠默认猜测。

AbilityTask：让单帧能力变成时序能力

GA 本体不是长时流程机，真正跨时间的行为由 AbilityTask 承担。
典型用法包括：

  1. 等待输入、等待事件、等待属性变化。
  2. 播放 Montage 并监听回调。
  3. 通过 RootMotionSource 驱动位移。

自定义 Task 的最小骨架建议固定下来：

  1. 静态创建函数。
  2. Activate 绑定外部委托。
  3. OnDestroy 清理委托与状态。
  4. 需要逐帧逻辑时启用 TickTask。

批处理：把 2-3 次 RPC 压缩成 1 次

常规技能链路里，激活、发目标数据、结束常常是多次 RPC。
对于“单帧内完成”的能力（例如半自动射击），Ability Batching 可以显著减负：

  1. 打开 ASC 的批处理开关。
  2. 用 FScopedServerAbilityRPCBatcher 包住激活窗口。
  3. 在同作用域内完成可合并调用。

对高频技能来说，这一步是很现实的网络优化收益点。

实战建议

这一阶段我最推荐的策略是：

  1. 先把 GA 生命周期日志打全，再做复杂能力组合。
  2. 对本地预测能力，先写失败回滚路径，再写表现细节。
  3. 把可重用的输入绑定、批处理、Task 封成基类能力，减少复制粘贴。

小结

GA 真正复杂的部分从来不是“写一个技能”，而是“长期维护十几个技能还能稳定迭代”。
