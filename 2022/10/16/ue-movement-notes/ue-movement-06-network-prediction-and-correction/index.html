系列定位：UE5 移动系统源码拆解（5.4/5.5）
本文主题：读通 CMC 网络移动闭环，并给出抖动/回弹排障路径

写在前面

网络移动这块最容易被一句“延迟高”带过去。
但多数抖动问题其实能拆开：预测、重演、纠偏、平滑，具体是哪一段出了偏差。

调用链图

关键函数定位

  • FSavedMove_Character：客户端每帧输入与状态快照。
  • UCharacterMovementComponent::ReplicateMoveToServer：客户端发送移动数据入口。
  • UCharacterMovementComponent::ServerMove*：服务器接收并重演移动。
  • UCharacterMovementComponent::ClientAdjustPosition*：服务器纠偏下发。
  • UCharacterMovementComponent::SmoothClientPosition：客户端视觉平滑，减少硬回弹。

我会怎么跟源码

这块我一般按“预测 -> 校验 -> 纠偏 -> 平滑”四段读：

  1. 打开 Engine/Source/Runtime/Engine/Private/Components/CharacterMovementComponent.cpp。
  2. 搜索 ReplicateMoveToServer(，确认客户端如何打包并发送移动。
  3. 搜索 ServerMove_（或 ServerMove(）系列函数，查看服务器重放与校验逻辑。
  4. 搜索 ClientAdjustPosition 系列函数，确认纠偏触发与参数下发。
  5. 搜索 SmoothClientPosition(，排查时重点对照 correction 频率和本地平滑窗口是否匹配。

可复现问题案例

复现步骤

  1. 在网络模拟中设置中高延迟与抖动（例如 120ms RTT + 抖动）。
  2. 角色连续冲刺并频繁转向。
  3. 打开移动日志，观察 correction 次数与位移误差。

现象

客户端频繁出现“向前一步再被拉回”，镜头有明显抖动感。

根因定位

本地预测轨迹与服务器重演轨迹持续偏离，ClientAdjustPosition 触发频率高；若平滑参数不足或自定义速度改动未进入 SavedMove 压缩数据，回弹会更明显。

最小修复策略

先确认自定义移动变量是否正确写入/恢复 SavedMove；再调 NetworkSmoothingMode 和平滑时间窗，最后对 correction 触发阈值与冲刺状态切换时机做联合排查。

收尾

网络移动稳定，不是追求“零纠偏”，而是纠偏可控、平滑自然。
把 SavedMove 生命周期看透后，抖动和回弹会好查很多。

深入一层：UE 网络移动其实是“可重演模拟”

这块最重要的不是 RPC 名字，而是一个原则：
客户端和服务端要尽量在“相同输入、相近时间步”下跑出相近结果。

CharacterMovementComponent.h 在 2327 行附近的注释其实已经把模型写明白了：

  1. 客户端保存 move。
  2. 客户端本地先模拟，再发给服务端。
  3. 服务端重演并校验。
  4. 误差大就下发 ClientAdjustPosition。
  5. 客户端回到服务器状态后重放未确认 move。

这就是“预测 + 纠偏 + 重放”的闭环。

源码主链（UE_5.5）

你可以按这组函数跟读：

  • CharacterMovementComponent.cpp:8666 ReplicateMoveToServer
  • ...:8897 CallServerMovePacked
  • ...:9619 ServerMovePacked_ClientSend
  • ...:9637 ServerMovePacked_ServerReceive
  • ...:9723 ServerMove_PerformMovement
  • ...:10928 ClientAdjustPosition_Implementation
  • ...:8365 ClientUpdatePositionAfterServerUpdate
  • ...:8129 SmoothClientPosition

这几段连起来就是完整闭环。

ReplicateMoveToServer 做了什么

在 ReplicateMoveToServer（...:8666）里，核心流程是：

  1. 检查控制器同步状态（避免可靠队列被淹）。
  2. 通过 UpdateTimeStampAndDeltaTime 对齐时间步。
  3. 创建 FSavedMove_Character，记录这帧输入和状态。
  4. 尝试与 PendingMove 合并，减少带宽。
  5. 本地执行移动并把 move 打包发送。

一个非常关键的细节是它会模拟服务端的 DeltaTime 取法，减少两端浮点误差。
这就是为什么看起来只是“时间戳处理”，但对抖动影响巨大。

FSavedMove_Character 里真正存了什么

从 CharacterMovementComponent.h:2894 开始看类定义，你会发现它不只是存输入方向：

  • TimeStamp / DeltaTime
  • StartLocation / SavedLocation
  • StartVelocity / SavedVelocity
  • StartPackedMovementMode / EndPackedMovementMode
  • CompressedFlags（jump/crouch/custom flags）

换句话说，它是“可重演所需最小状态快照”。
你自定义移动如果有关键状态没进 SavedMove，客户端和服务端一定跑偏。

CallServerMovePacked 的价值

CallServerMovePacked（...:8897）本质是把 move 数据写进 bit stream：
先 ClientFillNetworkMoveData，再序列化，再通过 ServerMovePacked 发出。

这套 packed 路径比旧 RPC 更省带宽，也更统一。
你如果在项目里做了自定义网络移动，通常也应该沿这套容器扩展，不要走散装参数 RPC。

服务端怎么重演

ServerMovePacked_ServerReceive（...:9637）会先反序列化，再走 ServerMove_HandleMoveData，最终到 ServerMove_PerformMovement（...:9723）。

ServerMove_PerformMovement 里有几个关键动作：

  1. 校验时间戳 VerifyClientTimeStamp。
  2. 计算服务端这次 move 的 DeltaTime。
  3. 应用客户端控制旋转和压缩 flags。
  4. 真正执行移动并做误差判断。

这解释了一个常见现象：
“客户端看着很顺，服务端仍然频繁纠偏”通常是时间步或状态恢复不一致，不是单纯延迟问题。

ClientAdjustPosition_Implementation 之后发生什么

在 ClientAdjustPosition_Implementation（...:10928）里，流程非常明确：

  1. 根据时间戳找到并 Ack 对应 move。
  2. 把服务器位置/速度/模式当权威写回本地。
  3. ApplyNetworkMovementMode(ServerMovementMode) 同步模式。
  4. 置 bUpdatePosition = true，下一帧触发重放。

下一步就是 ClientUpdatePositionAfterServerUpdate（...:8365）：

  1. 重放所有未确认 move。
  2. 恢复必要状态。
  3. 继续本地预测。

所以“回弹”通常不是设置位置那一帧造成的，而是“校正 + 重放”两段叠加后在视觉上体现出来。

平滑层 (SmoothClientPosition) 的职责边界

SmoothClientPosition（...:8129）只管视觉插值，不改权威物理结果。
它内部是：

  1. SmoothClientPosition_Interpolate
  2. SmoothClientPosition_UpdateVisuals

这层能解决“看起来抖”，但不能解决“模拟本身跑偏”。
如果 correction 频率很高，你只调平滑参数通常是治标不治本。

什么时候一定要扩展 SavedMove

出现下面任一情况，就不要只改本地变量：

  1. 自定义冲刺会改 MaxSpeed/Acceleration。
  2. 自定义模式切换会改变可输入方向或重力方向。
  3. 某些能力会改变碰撞响应或制动规则。

这些都会影响服务端重演结果。
如果不把关键状态压进 SavedMove 和 move data，校正频率会飙升。

我常用的网络移动排查顺序

  1. 先看 ReplicateMoveToServer 的发送频率和时间戳是否连续。
  2. 再看 ServerMove_PerformMovement 是否频繁判定误差。
  3. 再看 ClientAdjustPosition 后是否立即进入大量重放。
  4. 最后再调 SmoothClientPosition 参数。

这套顺序能避免“还没定位根因就疯狂调平滑”的低效循环。

一句实话

网络移动最难的部分不是“写一个移动功能”，而是“让它可预测、可重演、可纠偏”。
你只要用这个标准看代码，很多看似复杂的分支都会变得有逻辑。
