本文主题：解决“技能看起来对不对”的核心问题，建立表现与同步的一致性策略

GameplayCue：把“玩法结果”翻译成“可见反馈”

GameplayCue（GC）负责粒子、音效、镜头等表现层反馈。
核心原则很简单：让玩法逻辑和表现逻辑解耦。

常见两类 GC：

  1. GameplayCueNotify_Static：一次性执行，适合瞬时冲击。
  2. GameplayCueNotify_Actor：有生命周期，适合持续特效。

如果使用 GameplayCueNotify_Actor，建议确认移除路径完整，避免出现加上去就永远不掉的残留效果。

本地 GC 与复制 GC 的取舍

每个 GC 事件本质都可能带来网络开销。
对于高频命中特效，优先考虑本地 GC：

  1. 子弹撞击、近战命中火花、纯视觉轨迹，适合本地执行。
  2. 明确影响玩法理解的持续状态，优先走复制链路。

一个硬性约束是：本地 Add 的 GC 应该本地 Remove，不要混用通道。

预测系统：它解决“手感”，不保证“万物可预测”

GAS 预测是为了减少输入延迟感，不是为了完全替代服务端权威。
实践里必须接受这个现实：

  1. 可预测：技能激活、部分 GE 应用、Tag/Cue 变化、Montage、移动。
  2. 不可预测：GE 移除、周期 GE。

因此冷却和 DOT 相关逻辑，经常会出现“本地感觉快、服务器实际慢”的错位。
这不是实现 bug，而是机制边界。

Prediction Key 与窗口

预测链路靠 Prediction Key 关联客户端预测与服务端确认。
一个很关键的细节是：默认预测窗口很短，常常只覆盖激活原子阶段。

如果你在延迟回调里还要继续预测，需要显式创建新的预测窗口，常见做法是配合 WaitNetSync。
但这会引入服务器等待客户端的时序风险，使用时要注意防滥用。

Targeting：目标数据不是“点一下就完事”

TargetData 是跨客户端/服务器传输目标信息的标准载体。
TargetActor 则是生成这份数据的执行者，负责：

  1. 目标采样与过滤。
  2. 确认/取消交互。
  3. 可视化标线（Reticle）生命周期。

工程上最常见的取舍：

  1. 立即型目标（瞬时射线）追求性能，弱交互。
  2. 非立即型目标（带确认）交互更完整，但链路更重。

结合案例看“表现 + 同步”

这一阶段我最有感触的几个实战模式：

  1. Stun：标签驱动取消与阻断能力，移动组件配合限速或禁动。
  2. Sprint / ADS：移动组件预测 + GA 状态切换，手感优先。
  3. Lifesteal / Crit：在服务端结算中统一处理，避免预测抖动。
  4. 随机数：客户端和服务端要有同源种子，否则表现和结果会分叉。

一条可执行的策略

如果你的项目正在做多人动作技能，我建议优先落这条顺序：

  1. 先确认哪些反馈必须可靠，哪些可本地近似。
  2. 再按反馈等级设计 GC 通道，而不是统一全复制。
  3. 对所有预测能力建立“失败回滚可观察”机制。
  4. 在 Targeting 侧先解决防作弊与一致性，再追求高级交互。

小结

“看起来对”这件事，本质上是同步策略、表现策略和设计预期共同作用的结果。
