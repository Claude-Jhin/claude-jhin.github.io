本文主题：如何在不破坏默认模式的前提下扩展自定义移动能力

写在前面

MOVE_Custom 真正难的不是“能跑起来”，而是“能长期维护”。
很多项目后期变难改，问题都出在切入切出协议没定义清楚。

调用链图

关键函数定位

  • UCharacterMovementComponent::SetMovementMode：模式切换入口，同时触发相关状态回调。
  • UCharacterMovementComponent::PhysCustom：自定义模式总分发。
  • UCharacterMovementComponent::OnMovementModeChanged：切换前后状态收尾与初始化。
  • UCharacterMovementComponent::SafeMoveUpdatedComponent：自定义模式下仍应复用的位移碰撞接口。
  • ACharacter::OnMovementModeChanged：角色层同步动画/表现状态的常用接点。

我会怎么跟源码

自定义模式我会先看“切换协议”，再看具体位移实现：

  1. 打开 Engine/Source/Runtime/Engine/Private/Components/CharacterMovementComponent.cpp。
  2. 搜索 SetMovementMode(，确认 MOVE_Custom 的切入和回切入口。
  3. 搜索 PhysCustom(，查看 CustomMovementMode 的分发结构。
  4. 搜索 OnMovementModeChanged(，确认切换时状态初始化与清理点。
  5. 断点建议：进入模式和离开模式各打一组断点，确认进入、持续、退出三段条件都能命中。

可复现问题案例

复现步骤

  1. 新增 MOVE_Custom（例如攀爬）并在条件满足时切入。
  2. 只在进入时设置模式，不处理退出时机。
  3. 从墙面边缘离开后观察角色状态。

现象

角色离开可攀爬表面后仍停留在 MOVE_Custom，出现悬空、输入异常或无法恢复 Walking。

根因定位

自定义模式只处理“进入”，没有建立稳定的“退出协议”（例如失去附着条件后切回 Falling），导致模式状态机悬挂。

最小修复策略

为每个 Custom 子模式明确三件事：进入条件、持续条件、退出条件；退出统一走 SetMovementMode，并在 OnMovementModeChanged 中做状态收尾。

排查顺序（实战版）

收尾

MOVE_Custom 想做稳，关键是生命周期闭环。
切入、持续、切出三段定义清楚之后，自定义能力才能和默认移动长期共存。

深入一层：MOVE_Custom 默认其实非常“薄”

很多人第一次看 MOVE_Custom 会以为 UE 已经帮你准备好了复杂框架。
实际上默认实现非常薄，在 UE_5.5 里：

  • PhysCustom（CharacterMovementComponent.cpp:6058）默认只调用 CharacterOwner->K2_UpdateCustomMovement(deltaTime)。

也就是说，UE 只给你一个分发入口，真正的运动学、碰撞策略、网络状态一致性都要你自己补。

模式切换的真实入口：SetMovementMode

你能控制自定义模式是否稳定，核心不在 PhysCustom，而在 SetMovementMode 和 OnMovementModeChanged：

  • SetMovementMode：...:1313
  • OnMovementModeChanged：...:1360

SetMovementMode 做了几件重要事：

  1. 非 MOVE_Custom 自动把 CustomMovementMode 清零。
  2. 拒绝无效的 NavWalking 场景（无 NavData 会回退）。
  3. 真正写入 MovementMode/CustomMovementMode 后调用 OnMovementModeChanged。

所以你在业务层直接改枚举变量，而不走 SetMovementMode，迟早会出状态不同步。

OnMovementModeChanged 为什么关键

OnMovementModeChanged 不只是一个通知钩子。
它会做一堆“模式切换后必须一致”的收尾动作：

  1. Walking 进入时：刷新地面、修正高度、设置 base。
  2. Falling 进入时：应用地面基座速度、触发 CharacterOwner->Falling()。
  3. None 进入时：清速度、清 jump state、清累计外力。
  4. 最后调用 CharacterOwner->OnMovementModeChanged(...)。

这意味着你做自定义模式时，如果切换时机错了，不仅自定义逻辑错，默认模式恢复也会错。

网络里 CustomMovementMode 是怎么发的

这一块经常被忽视。
在 PackNetworkMovementMode（...:1456）里，UE 会把模式压到 1 字节里：

  1. 非 custom：编码 MovementMode + GroundModeBit。
  2. custom：编码 CustomMovementMode + CustomModeThr。

对应解包在 UnpackNetworkMovementMode（...:1471），应用在 ApplyNetworkMovementMode（...:1489）。

这说明两件事：

  1. CustomMovementMode 本质就是一个 uint8 子模式号。
  2. 客户端/服务端必须对这个编号语义完全一致，否则一定错模式。

C++ 扩展时的推荐结构

如果你准备把它做成长期可维护方案，我建议：

  1. 定义清晰的 enum class ECustomMoveMode : uint8。
  2. PhysCustom 只做分发，不塞业务细节。
  3. 每个子模式拆成独立函数（PhysClimb/PhysWallRun/...）。
  4. 每个子模式都写“进入条件、持续条件、退出条件”。

自定义模式和默认模式互相污染的典型原因

原因 1：退出 custom 时不走 SetMovementMode

直接改 MovementMode 会绕开 OnMovementModeChanged，导致 floor/base/jump state 不一致。

原因 2：custom 里复写了速度但没约束重力平面

下个模式恢复后会出现速度方向突变，表现成“切回 Walking 突然抽动”。

原因 3：模式切换条件分散在多个类

一个在 Character，一个在 Anim，一个在 Movement，后期必然互相打架。

实战建议：把“协议”写进注释和日志

我一般要求每个 custom 子模式在代码里明确三条日志：

  1. Enter：为什么进来（命中了什么条件）。
  2. Tick：持续条件是否仍成立。
  3. Exit：为什么出去（失败条件是什么）。

这比后期看一堆断点快太多，尤其是联机环境。

和网络预测结合时要额外注意什么

只要 custom 模式会影响速度、方向、输入语义，就需要考虑 SavedMove 扩展。
否则客户端预测和服务端重演会使用不同状态，纠偏会非常频繁。

从工程角度看，MOVE_Custom 不是“只改本地物理”，它其实是“改一个需要预测和重演的状态机”。
